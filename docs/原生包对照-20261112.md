# 原生包对照：页面发布工作区 vs 生成器产物

> 样本来源：`http://pp6-test.example.com:8112` 后台「系统管理 › 发布管理 › 发布工作区」
> 采集时间：2026-11-12 12:25 / 12:30（两次发布）
> 产物：`docs/原生包样本-20261112/native-121225.zip`、`native-121230.zip`

这份文档只记**格式事实**与**生成器的差异**。改生成器前先看这里，别凭印象。

---

## 一、包本身

| 事实 | 取值 | 怎么确认的 |
|---|---|---|
| 目录层数 | **单层**，顶层就是 `bo/ form/ data_template/` | 解包直接看到，无外层文件夹 |
| 是否可混装 | **可以**，一个 zip 里三类并存 | `native-121230` 有 3 bo + 1 form + 2 data_template |
| 序号规则 | **跨目录连续**：`bo/001`、`bo/002`、`form/004`、`data_template/005` | 同上 |
| comment | `CONFIG_SYNC_NOTE:<发布说明原文>` | 页面「发布说明」输入框，上限 **500 字** |
| 文件命名 | `{三位序号}-{code}.xml` | 全部样本一致 |

> 「发布说明」就是 zip 的 comment。系统不写别的元信息，没有 manifest / catalog / 图标。

## 二、业务对象 `bo/*.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<tns:bodefs xmlns:tns="http://www.ankepower.com/iform-bo-def"
            xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
            xsi:schemaLocation="http://www.ankepower.com/iform-bo-def ../xsd/iform-bo-def.xsd">
  <tns:bodefentity id tblName code name dataformat="json" boType="object"
                   isCreateTable="Y" pk="id" typeId="" dsAlias="" desc=""
                   moduleId="" mode="normal">
    <tns:options><![CDATA[{...}]]></tns:options>
    <tns:attribute .../>
  </tns:bodefentity>
  <tns:boListColumnList/>
</tns:bodefs>
```

**attribute 的属性顺序**（严格按此排）：
`code, fieldName, name, desc, type, datatype, dataTypeNew, options, isnull, isindex, sn, length`

**系统字段的顺序与定义**（以 `pp_review_ext_check_item` 为准）：

| sn | code | datatype | dataTypeNew | length | isindex |
|---|---|---|---|---|---|
| 1 | `id` | varchar | varchar | 64 | Y |
| 12 | `tenantId` | varchar | varchar | 64 | Y |
| 13 | `ip` | varchar | varchar | 15 | N |
| 14 | `createBy` | varchar | user | 64 | Y |
| 15 | `createTime` | datetime | datetime | — | N |
| 16 | `updateBy` | varchar | user | 64 | Y |
| 17 | `updateTime` | datetime | datetime | — | N |
| 18 | `deleted` | varchar | varchar | **1** | Y |
| 19 | `version` | number | number | 20 | N |
| 20 | `processNode` | varchar | varchar | 300 | N |
| 21 | `processHandler` | varchar | varchar | 1000 | N |
| 22 | `processDefId` | varchar | varchar | 64 | N |
| 23 | `processInstanceId` | varchar | varchar | 64 | N |

三个容易看错的地方：

1. **`updateBy` 在 `updateTime` 前面**（16 / 17）。写成 updateTime → updateBy 是错的。
2. **`deleted` 是 `varchar(1)`**，不是 20。存的是 Y/N 单字符。
3. `datatype` 与 `dataTypeNew` **可以不同**：`selfAssigneeId` 是 `datatype=varchar` + `dataTypeNew=user`。
   前者是物理列类型，后者是控件语义，别混。

**系统字段不是固定模板**：不同对象的长度会变——`cs` 的 `createBy` 是 24、`pp_project_report` 是 32；
`pp_project_report` 的 `createTime` 甚至是 `date` 而不是 `datetime`。但 `deleted=varchar(1)` 没见过例外。

## 三、表单 `form/*.xml`

```xml
<form>
  <formDefs>
    <formDef id name key mode="bo" status="deploy" typeId formType="form"
             shared="Y" isMain="Y" version="1" extendAttr="{...}">
      <tenantId>-999</tenantId>
    </formDef>
    <formField id formId [parentId] name label [desc] fieldType fieldOptions [sn]/>
    <formBo id formId boId boCode/>
    <formRights id formKey code name permission type="field" rightsType="form" ...>
      <tenantId>-999</tenantId>
    </formRights>
  </formDefs>
</form>
```

### 容器类型（五个，混用）

| fieldType | name 前缀 | label | 结构 |
|---|---|---|---|
| `fieldset` | `fieldset_xxxxxxx` | 分区标题 | `columns` 只存子 id 引用，`span` 为空 |
| `card` | `card_xxxxxxx` | 卡片标题 | 同上 |
| `grid` | `grid_xxxxxxx` | 恒为「栅格布局」 | `columns` 存 id + `span`(8/12/24)，**无 `rows`** |
| `grid_layout` | `gridLayout_xxx` | 恒为「表格布局V1.0」 | `columns` + `rows` 两份 |
| `collapse` | `collapse_xxx` | 折叠面板名 | `columns` 里带 `label` |

### 两种布局的本质区别（最容易搞混）

- **`grid`（栅格布局）**：只有 `columns`，子控件的 **`sn` 全是 1**。
  系统按 `span` 自己排，`sn` 不参与排序。
- **`grid_layout`（表格布局V1.0）**：`columns` 存 id 引用，`rows` 存**完整字段副本**
  （含 `field_type/label/icon/field_options/field_name/modelKey`），子控件 `sn` **递增 1..N**。
  两份必须一致，缺一份该格就空着。

### 明细表 `dataTemplate`

```xml
<formField id="..." parentId="<容器id>" name="xmhbfxxb" label="未关闭的风险"
           fieldType="dataTemplate" fieldOptions="{...}" sn="1"/>
```

**它不经过 `grid_layout`**：容器的 `columns` 直接引用控件 id。
`fieldOptions` 关键键：

```json
{
  "bind_template_key": "xmhbfxxb",
  "name": "未关闭的风险",
  "hide_label": true, "hide_border": true, "hide_border_bottom": true,
  "heightMode": "fixed", "heightUnit": "px",
  "mappingFields": [], "casadeFields": [],
  "isAlldata": false, "notInputCondition": "conditionIsNone",
  "autoCollapse": true, "top_margin": 10, "bottom_margin": 10, "is_margin": false,
  "params": [{"key":"reportId","type":"varchar","valueType":"bo","value":"id","label":"reportId"}]
}
```

`mappingFields` / `casadeFields` 即使为空也要写，省掉导入后子表不渲染。
`params` + `casadeFields` 是父→子传参（父表单 id 写进子表外键），**生成器暂未支持**。

### 其他

- `formDef.typeId` **可以留空**（WeeklyReport 就是空），不是必填
- `formRights` 每个控件一条，外加一条 `name="_p_title"`（表单标题）
- `sn` 在同一父级下从 1 开始；根级（无 parentId）的 `sn` 是文档顺序

## 四、列表 `data_template/*.xml`

```xml
<dataTemplate>
  <dataTemplateDefs>
    <dataTemplateDef id datasetKey name key typeId="" type="default"
                     showType="dimension" composeType="treeList"
                     unique="id_" uniqueField="id_" attrs="{...}"
                     createBy createTime updateBy updateTime>
      <tenantId>-999</tenantId>
    </dataTemplateDef>
    <dataTemplateField id templateId name="<物理表名>" label="<列表名>" objName="<物理表名>"/>
    <dataTemplateTpl id templateId displayColumns filterConditions functionButtons attrs/>
    <dataSet id name key type="table" external="N" dsAlias="dataSource_default"
             from="<物理表名>" parentFrom="" sql="" isTree="N" isDefaultSort="Y"
             dataFrom="singleTable" dataTables="" selectFields="" joinFields=""/>
  </dataTemplateDefs>
</dataTemplate>
```

- `dataTemplateTpl` **一个视图一条**：`5_列表` 的「视图类型」填 `grid,board` 就是两条
- `dataTemplateField.name` 是**物理表名**（`pp_project_report_issue_item`），不是对象编码
- `dataSet.key` 与 `dataTemplateDef.datasetKey` 必须一致

## 五、与生成器产物的差异

### 已修（2026-11-12）

| # | 项 | 原状 | 现状 |
|---|---|---|---|
| 1 | `deleted` 长度 | `varchar(20)` | `varchar(1)` |
| 2 | 系统字段顺序 | `updateTime` 在 `updateBy` 前 | 调成 `updateBy` → `updateTime` |
| 3 | 明细表控件 | 退化成 `text`（子表在表单上是个文本框） | 支持 `dataTemplate`，容器直挂、不经 `grid_layout` |
| 4 | 控件类型校验 | 不管 | `number`/`datetime` 字段填 `text` 控件时报 warn |
| 5 | 反解 `dataTemplate` | 不读 `bind_template_key` | 读进「取值来源」列 |
| 6 | **自定义日期字段在界面上凭空消失** | 生成 `isDefault:true` 的 datetime，平台当成系统时间戳隐藏：对象属性页「共计」比实际少 1 | 日期字段 `isDefault` 默认 false；`options` 按原生补全 8 键；属性 `format` 去掉秒 |

### 未修（已知差距）

| # | 项 | 影响 | 备注 |
|---|---|---|---|
| 1 | 明细表 `params`/`casadeFields` | 子表拿不到父记录 id，需要在设计器里手工绑 | 要拿到「父对象子表外键字段」才能自动填 |
| 2 | `grid`（栅格布局）未产出 | 生成器只出 `grid_layout`，体积偏大 | 功能不受影响；简单表单可用 `grid` 更轻 |
| 3 | `formDef.typeId` 留空 | 原生多数有值、也有空的 | 留空能导入，界面分类可能进「未分类」 |
| 4 | `dataTemplateDef.createBy/updateBy` 留空 | 列表的「创建人」显示空 | 需要填真实用户 id |
| 5 | 反解 5 个既有错误 | 隐藏规则依赖控件缺失（3）、列表视图类型被当成容器名（2） | 与本次改动无关，基线同样失败 |

## 五之二、导入后在线上能改什么（2026-11-12 实测）

这条是用户最常问的：「包导进去以后，字段类型我在线改还能生效吗？」
结论不是"能/不能"，而是**分类型**。

### 判定规则（前端硬编码，不是权限问题）

`platform.bo.bo-def` 的属性抽屉里有这段判定：

```js
dataTypeDisabled() {
  return !!this.existingRelationshipAttr
      || ("default" === this.listType && !this.isOut && !this.isDefaultAuditUserAttr
          || !this.isNewData && !equalAttrsMap.includes(this.form.dataTypeNew))
}
const equalAttrsMap = ["varchar","user","department","object","userGroupCate","autoNumber","dic"]
```

翻译：**字段已存在时，只有 varchar 族（字符串/用户/部门/选项/对象/用户组/自动编号）的类型下拉可点**，
`number` / `datetime` / `clob` / `date` 一律置灰。原生对象同样如此——不是我们包的问题。

原因是物理层：这一族在库里都存成 `varchar`，互相改不碰表结构；
改 `number ↔ varchar` 要 `ALTER TABLE`，平台不给线上做。

### 实测证据

| 对象 | 字段 | 类型 | 抽屉里「数据类型」 | 下拉 |
|---|---|---|---|---|
| 我们生成的 `zz_typetest` | tQty | number | `disabled=true`（`is-disabled`） | 点不开 |
| 我们生成的 `zz_typetest` | tName | varchar | `disabled=false` | 展开 7 项 |
| 平台原生 `项目立项信息` | applicantPhone | varchar | `disabled=false` | 展开 7 项 |

改完真的落库了：tName 从 `varchar` 改成「用户」后，`bo/def/manage` 返回
`dataType=varchar, dataTypeNew=user` —— **`dataType`（物理列）不变，只改语义类型**，
这正是同族可改的原因。

### 操作路径（自动化也按这个走）

```
数据 › 业务对象 › 卡片点进详情 › 页签「对象属性」
  → 表格是 <canvas> 画的（DOM 里查不到行）
  → 改类型不是点「铅笔」，而是**在行上右键**打开右侧抽屉
  → 抽屉里「数据类型」下拉 → 选同族类型 → 「保存」
```

> 坑：这个表格是 canvas，`document.querySelectorAll('tr')` 只有 1 个表头行，
> 按文本也搜不到字段名。自动化必须用坐标（截图坐标 = 视口坐标，注意别被显示缩放骗了）。

### 还没验证的边界

- 改完 BO 字段类型后，表单设计器里的控件是否会跟着变**没验**（控件类型是表单层的
  `fieldType`，两层独立；`form/def/manage` 返回的 `formHtml` 是空的，只能进设计器看）。
- 改类型是否触发历史数据转换：本次测试对象无数据，未覆盖。

## 六、复核方法

```bash
# 1. 反解成 Excel
.venv/bin/python -m pp6kit inspect docs/原生包样本-20261112/native-121230.zip -o /tmp/样本.xlsx

# 2. 重出包
.venv/bin/python -m pp6kit build /tmp/样本.xlsx -o /tmp/out

# 3. 结构契约
.venv/bin/python tools/check_form_layout.py /tmp/out

# 4. 逐项对照（本文件第二节的字段表）
unzip -p /tmp/out/整包/*.zip bo/001-*.xml | head -c 2000
```

样本包已入库（228K，纯结构定义、不含业务记录）。原始抓取的 7.9M JSON 快照在
`docs/线上抓取-20261112/`，按客户数据口径 gitignore，不入库。
