> 本文件由 `python tools/regress.py --report docs/测试用例清单.md` 生成，
> 内容直接来自 `tests/` 里的用例注册表——**不要手改**，改了会在下次生成时被覆盖。

共 272 条；核心链路 143 条。

## 什么时候跑

- 每次往 app 里迁功能（改 `pp6kit/`、`assets/`、`static/`）→ 全量跑一遍；
- 只改前端 → 至少跑 `-m webui -m security`；
- 新增功能 → 在对应 `tests/test_*.py` 里加用例（见文末「加用例的规矩」）。

```bash
./.venv/bin/python tools/regress.py            # 全量
./.venv/bin/python tools/regress.py --list     # 只看清单
./.venv/bin/python tools/regress.py -m patch   # 只跑改包
```

| `NLQ67` | 核心 | 一个对象都认不出来时明确报错，而不是乱选一张 | 选错表比报错更糟：用户会相信那个数字、不测会怎样：问「今天天气」也返回一张业务表的全量数据 |
| `NLQ68` | 常规 | schema linking 带上外键目标表、去重且不超上限 | 大模型要写子查询就必须看到关联表，但全表塞进 prompt 会爆 token、不测会怎样：模型看不到 pp_customer 就编一个不存在的列名 |
| `NLQ69` | 常规 | 排除/不包含/去掉这类否定都识别得出来 | 否定识别错方向，条件就从「排除」变成「只看」、不测会怎样：「排除状态是已关闭的」返回的全是已关闭的项目 |
| `NLQ70` | 核心 | 普通问句不会被误判成否定 | 误判否定会把正常条件翻成 NOT LIKE，结果反过来、不测会怎样：「有风险的项目」返回「没有风险的项目」 |
| `NLQ71` | 常规 | 「未完成」不算子句否定（值级否定另有出口） | 「未完成」是对**值**的否定，不是对子句的否定、has_negation 只判子句级（排除/不包含）；值级由 NEG_PAIRS 翻成「已…」、不测会怎样：把「状态未完成」写成 NOT LIKE '%完工%' 反而查不到 |
| `NLQ72` | 常规 | 否定词的作用域只看条件前一小段 | 否定词离得太远就不该影响这个条件、不测会怎样：一句话里前一个「没有」把后面所有条件全翻成否定 |
| `NLQ73` | 常规 | 归一化去掉空格与「的/地/得」 | 问句和字段标签之间差一个「的」就匹配不上、不测会怎样：「项目的名称」认不出「项目名称」这个字段 |
| `NLQ74` | 核心 | 空问题明确报「无法理解」而不是编一条 SQL | 用户误点回车时不该去查生产库、不测会怎样：空问题产出一条全表查询，白扫 20 万行 |
| `NLQ75` | 核心 | 规则引擎产出的 SQL 全部能过安全闸 | 规则引擎是另一条生成路径，同样不能绕过 guard、不测会怎样：规则引擎拼出的 SQL 带写操作或多表，直接打到生产库 |
| `NLQ76` | 核心 | 选列问句带软删除过滤且用 IFNULL 包裹 | 平台上 deleted_ 有三种写法并存（全 NULL / N-Y / Y-N）、不测会怎样：`deleted_ <> 'Y'` 会把全 NULL 的表整表过滤光（pp_task 601 行变 0 行） |
| `NLQ77` | 核心 | 中文枚举值被翻译成库里存的码 | state_ 里存的是 inprogress，不是「进行中」、不测会怎样：用中文去 LIKE 一个英文码列，永远返回 0 行 |
| `NLQ78` | 核心 | 否定条件写成 NOT LIKE | 「不能包含测试」写错方向就等于「只看测试」、不测会怎样：用户拿到完全相反的清单 |
| `NLQ79` | 核心 | 分组统计问句生成 COUNT + GROUP BY + 关联表 | 「每个项目有多少需求」是最常问的一类、不测会怎样：只 COUNT 不 GROUP，用户拿到一个总数却以为看到的是分布 |
| `NLQ80` | 核心 | 排名问句生成 ORDER BY DESC + LIMIT N | 「进度最高的5个项目」不排序就是随机 5 个、不测会怎样：老板看到的「最高 5 个」其实是随便 5 个 |
| `NLQ81` | 常规 | 平均/合计问句不能生成 AVG(*) 这种非法聚合 | AVG(*) / SUM(*) 在 MySQL 里是语法错误，整条 SQL 直接执行失败、而 sqlglot 能解析它、安全闸也看不出问题，坏 SQL 会直达客户库、不测会怎样：所有「平均/合计」问句要么报错要么走 AI 重试，规则引擎白跑 |
| `NLQ82` | 常规 | 完全没意义的问句要抛 NotUnderstood 而不是给全表结果 | local.build 的 docstring 承诺「解析不了的会明确说解析不了」、「有数据 +3 / 有名称列 +2」这类结构分只该用来排同分，不该让一张没被提到的表变成候选、不测会怎样：用户输入乱码也返回一张业务表的全部数据，看起来像答对了 |
| `NLQ83` | 边界 | 数值列不会被写成 LIKE '%高%' | progress_ LIKE '%高%' 在 MySQL 里恒不匹配，静默返回 0 行、不测会怎样：用户问「高进度的项目」，得到一张空表还以为真的没有 |
| `NLQ84` | 常规 | 普通问句不会被语义模板劫持 | 语义模板是硬编码 SQL，命中即优先于规则和历史示例、不测会怎样：一句普通问句命中报表模板，用户拿到完全不相干的报表 |
| `NLQ85` | 常规 | 0 行时判断「这个结果是不是可疑」 | 0 行不报错但结果错，比报错更难发现、不测会怎样：条件写歪导致空表时不做一次自查，用户直接拿到空结果 |
| `NLQ86` | 核心 | 删库/删表/删数据类问句一律拒绝生成 | 用户要的是「拒绝输出」，不是「输出了再警告」、不测会怎样：有人问「清空任务表」，界面上真给他一条 DELETE，复制去库里就是事故 |
| `NLQ87` | 核心 | 「已删除/删除标记」这类定语不算破坏意图 | 「删除」在正常问句里到处都是：已删除的项目、删除标记、删除时间、不测会怎样：为了拦删库把「查已删除项目」这种正经需求一起打死 |

## 加用例的规矩

1. 在对应模块的 `tests/test_<模块>.py` 里写函数，用 `@case("前缀NN", ...)` 登记；
2. 编号在模块内递增，**已发布的编号不复用**（删了就留空号）；
3. 标题写「用户能感知的行为」，不写「测试某函数」；
4. `tags` 填这条用例真正守住的东西（如「物理列名不变」），回归失败时一眼看出影响面；
5. 断言要基于**真实产出**（解 zip、读 XML），不要只断言中间变量；
6. 加完跑 `./.venv/bin/python tools/regress.py -m <模块>`，再 `--report` 更新本文件。

### 新功能迁入时的最小动作

- 新增一个 HTTP 接口 → 在 `test_webui.py` 补一条「正常返回」+ 一条「坏输入 400」；
- 新增一种字段类型 → 在 `test_bo.py` 与 `test_form.py` 各补一条，断言 XML 里的真实属性；
- 改了生成逻辑 → 先跑全量确认无退化，再把新行为补成用例；
- 只能人工确认的（连库、大模型）→ 用 `skip("原因")`，并在验收单里注明手工步骤。
