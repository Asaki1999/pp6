# AI 助手动作：把 DBX 的 Ask / Agent 搬到 pp6

> 2026-11-27。用户给了 DBX 两屏菜单截图，要求「图中的我都想要」。
> 这份文档记录**每个动作落在哪、为什么不完全照抄**，以及改坏哪一行会出事。

## 一、菜单对照

| DBX Ask | pp6 动作 | 会执行？ | 落地位置 |
|---|---|---|---|
| 自动 | `auto` | **会**（有 Key 直接调模型，模型不可用才回退本地规则） | `webui._nlq_ask_impl` 走 engine=auto |
| 通用问答 | `chat` | 否 | `assist._run_ask` + `_ASK_PROMPTS["chat"]` |
| 生成 SQL | `generate` | 否 | `assist` 复用 `engine.build_messages` |
| 解释 SQL | `explain` | 否 | 有 Key 走模型；没 Key 走 `local_explain` 语法摘要 |
| 优化 SQL | `optimize` | 否 | `_ASK_PROMPTS["optimize"]`，产物过 `_judge_output` |
| 修复错误 | `fix` | 否 | 同上；前端在报错条上给「用 AI 修复」入口 |
| 转换方言 | `dialect` | 否 | `_ASK_PROMPTS["dialect"]`，目标方言走 `DIALECT_TARGETS` |
| 生成样例 | `sample` | 否，且**永远不可执行** | 产出 INSERT，`executable=False` |

| DBX Agent | pp6 动作 | 走哪条路 |
|---|---|---|
| 自动 | `auto` | 有 SQL → `run_explain`，没有 → `query` |
| 通用问答 | `chat` | `_agent_loop(want="answer")` |
| 查询数据 | `query` | `agent.run`（原有的查证闭环） |
| 查看表结构 | `schema` | `_agent_loop(want="answer")` + 表格提示词 |
| 执行并解释 | `run_explain` | `agent.run` 执行 + 一次结果解释调用 |
| 生成但不执行 | `dryrun` | `_agent_loop(want="sql")`，拿到 SQL 就停 |

## 二、一处刻意调整：Ask·自动

DBX 的「自动」是「按内容判断该做什么」。pp6 的 Ask·自动是：**有 Key 就直接调大模型，
没配 Key 或模型全挂才回退本地规则**。

第一版写的是「规则优先」（`hybrid`），当天被用户否掉了，原话是「内置的规则 SQL 屁用没有」。
理由成立：`nlq/local.py` 那套打分选表是靠 142 条语料调出来的，覆盖有限；让它先跑，
等于让一个猜得不准的东西决定答案，猜错才叫 AI 补救。回归 `NLQA15` 锁死这个默认值。

规则引擎的新定位，三条，按可信度排序：

1. **人工修正**：用户手改过的 SQL，同样的问句直接复用（`_ask_local` 第 ① 级）。
2. **AI 答案的缓存**：AI 答对并沉淀进示例库的问答（第 ②③ 级），比规则自己造的可信。
3. **离线兜底**：没 Key 或渠道全挂时，`local.build` 才上场（第 ④ 级）。

也就是说规则不再是主路径，而是「缓存 + 断网时的最后一手」。

想让模型只生成不执行，显式选「生成 SQL」或 Agent 的「生成但不执行」。

## 三、安全边界

1. **Ask 的动作一律不执行**。唯一例外是 `auto`（走 hybrid 老路径）。
2. **产物打标**：所有 SQL 都过 `guard.is_read_only`，不是只读的标 `executable=False`，
   前端据此禁用「重新执行」，也进不了示例库。
3. **样例永远不执行**：`sample` 产出 INSERT，`warning` 写明「只展示、不执行，
   请复制到测试库运行」。回归 `NLQA05`。
4. **方言转换不套 MySQL 的闸**：目标写法的 LIMIT/函数都不是 MySQL 的，
   展示模型原样输出，`executable=False`。
5. **解释跳过问句闸**：解释一条 DELETE 不碰库，不该被当成注入拒掉；
   其余会执行的动作照旧先过 `screen_question`。

## 四、改坏哪一行会出事

| 位置 | 后果 |
|---|---|
| `assist._judge_output` 恒返回 executable=True | 模型给的 DELETE 会亮着「重新执行」 |
| `ACTIONS["ask"]` 里给 `sample` 加 `executes=True` | 点一下往客户库插测试数据 |
| `_nlq_ask_impl` 把自动改回 `engine="hybrid"` | 配了 Key 的用户又被规则引擎先答一遍 |
| `assist.split_code` 的语言标记判据放宽成「纯字母」 | ```INSERT 整行被当标记删掉，样例只剩空框 |
| `assist.agent_messages` 复用 `engine.SYSTEM` 全文 | 「查看表结构」返回一段 SQL 而不是表格 |

## 六、下一步

- 「修复错误」目前只能从报错条触发，也可以让它读 `#qSql` 自己先跑一次拿报错（多一次执行，未做）。
- 方言转换只覆盖 MySQL → 其它；反向（PG → MySQL）没接，提示词里也没写。
- 「生成样例」依赖 introspect 的采样值填外键；跨表外键多时模型仍可能填错，需要真实库验证。

## 七、第二轮：连续查询

第一轮解决的是「一次问对」，第二轮解决「查完之后还能接着做什么」。四件事：

### 1. 追问上下文（`context`）

结果出来后，输入框上方挂一条「接着问：xxx ×」。下一次请求带上
`context: {question, sql}`，后端拼进提示词（`engine.context_block`）。

提示词里有一句必须留着：**「如果新问题与上一轮完全无关，就忽略这段」**。
实测两组：

| 追问 | 结果 |
|---|---|
| 「只看执行中的」 | 保留 GROUP BY，只加 `AND s.name_ = '执行中'`，返回 1 行 |
| 「改成按项目类型分组」 | 换掉 JOIN 与 GROUP BY，结构正确 |
| 「最近创建的风险有哪些」 | 完全忽略上一轮，切到 `pp_risk` |

链路要三处都透传：`engine.build_messages` / `agent._system` / `assist.build_messages`。
断任何一节都会静默失效（界面有条、模型没看到），回归 `NLQA18/19` 守着。

### 2. 最近查询（`~/.pp6kit/query_history.json`）

30 条，只存问句 / SQL / 行数 / 耗时，**不存结果行**（客户数据不复制到第二个文件）。
同问句 + 同 SQL 只留最新，避免反复「重新执行」刷屏。原子写（`.tmp` + `replace`）。

不复用 `nlq.json`：那份是配置 + 示例库，每次保存整体重写，历史是高频写入。

### 3. 结果内筛选与排序

纯前端。表头点击「升序 → 降序 → 取消」，顶部一个筛选框对全部列做 contains。
几百行里找一行，比回头改 SQL 加 WHERE 快，也不用再花一次模型调用。

### 4. 截断与慢查询提示

`guard.MAX_ROWS = 500`。结果正好 500 行时标「可能被截断」——不标的话，
用户会拿前 500 行当全量去汇报。耗时超 5 秒标「较慢」。

## 八、还没做的（按价值排序）

| 候选 | 为什么值得 |
|---|---|
| SQL 差异对比 | 优化 / 修复后让人肉眼比两条长 SQL，是现在最痛的环节 |
| 一键 EXPLAIN | 跑之前就知道会扫多少行，比跑完等 8 秒好 |
| 结果自动出图 | 分组 + 数值型结果，柱状图比表格快 |
| 收藏查询 | 现在的「存为示例」是给 AI 学的，不是给人点的快捷入口 |
| 追问建议 | 结果下方给 2–3 个「你可以接着问」，降低上手门槛 |
| schema 缓存 TTL | 库加字段后要改一次配置才刷新 |

不建议做的：SQL 语法高亮 / 补全（要引 CodeMirror，体积与复杂度不划算）、
执行计划可视化树（收益低于成本）、自由多轮闲聊（会退化成通用 chatbot）。
