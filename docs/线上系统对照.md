# PowerProject V6 线上系统对照学习记录

> 通过 Playwright（复用本机 Chrome）登录 `http://pp6-test.example.com:8112/` 抓取的真实接口与数据结构。
> 目的：对照验证 pp6kit 生成器的 XML 结构是否与系统真实格式一致。
> 抓取时间：2026-10-27。系统版本：Version 6.0_26.1026.2350。

## 一、真实接口规范（重要，与猜测完全不同）

### 1. 接口前缀

所有业务接口走网关，前缀是：

```
http://<host>:8112/gateway/powerproject/<服务域>/v3/...
```

按服务域分四类：

| 服务域 | 用途 | 示例 |
|---|---|---|
| `oauth2` | 认证 | `/oauth2/v3/user/login/apply` |
| `platform` | 平台基础 | `/platform/v3/file/getImage` |
| `business` | **业务对象/表单/数据** | `/business/v3/bo/def/query` |
| `pp-project` | 项目业务 | `/pp-project/v3/api/userHome/...` |

> ⚠️ 前端 JS 里写的路径（如 `/bo/def/importBo`）只是相对路径，
> 真实请求要拼上 `gateway/powerproject/business/v3` 前缀。
> 之前从 JS 提取的 1289 个路径，都要这样理解。

### 2. 统一响应包裹

所有接口返回同一层外壳：

```json
{
  "state": 200,        // 非 HTTP 状态码，是业务码
  "type": "success",
  "request": null,
  "message": "",
  "cause": "",
  "variables": {},
  "data": { ... }      // 真正的数据
}
```

### 3. 双层 JSON 编码（关键陷阱）

部分接口（如 `bo/def/manage`）的 `data` 字段是**字符串化的 JSON**：

```json
{ "state": 200, "data": "{\"code\":\"...\",\"attrs\":[...]}" }
```

解析时要 `json.loads(json.loads(body)["data"])` 二次解码。

### 4. 认证方式

- 登录：`POST /oauth2/v3/user/login/apply`，body 里密码是前端加密后的（非明文）
- 之后所有请求带 `access_token`（JWT，`eyJ...` 开头），放在 URL query 或 header

## 二、业务对象真实结构

### 列表接口 `POST /business/v3/bo/def/query`

```json
{
  "data": {
    "dataResult": [ { 对象... } ],
    "pageResult": { ... },
    "total": 187
  }
}
```

单个对象字段（列表态，不含字段明细）：

| 字段 | 含义 | 取值 |
|---|---|---|
| `id` | 18 位雪花 ID | "1513648060884844544" |
| `code` | 对象编码 | "test_case_base_category" |
| `name` | 对象名称 | "测试用例库大类" |
| `boType` | 对象类型 | `object`（普通）/ 流程对象 / 状态机对象 |
| `isCreateTable` | 是否建物理表 | `Y` / `N` |
| `status` | 状态 | `actived` |
| `mode` | 对象选择模式 | `normal`（普通业务对象）/ `workflow`（流程模式）——流程对象必须是 `workflow`，否则流程定义挂不上 |
| `isMain` | 是否主表 | `Y` |
| `typeId` | 分类 ID | "1439939282688020480" |
| `moduleId` | 模块 ID | "1504408725908094976" |
| `dataFormat` | 存储格式 | `json` |
| `options` | 对象配置 JSON 字符串 | 见下 |

`options` 反序列化后：

```json
{
  "struType": "list",
  "idKey": "id",
  "pIdKey": "id",
  "key": "id",
  "formKey": "private_condition_xxx",   // 条件专用表单 key
  "uniqueRules": []
}
```

### 详情接口 `POST /business/v3/bo/def/manage?boDefId=xxx`

返回 `data` 是**字符串化 JSON**，二次解析后：

```json
{
  "code": "test_case_base_category",
  "tblName": "pp_test_case_base_category",   // 物理表名 = pp_ + 编码
  "boType": "object",
  "options": { ... },
  "attrs": [ { 字段... } ]
}
```

### 字段（attrs 元素）完整结构

```json
{
  "id": "1564274076682289152",
  "defId": "1513648060884844544",
  "code": "name",                    // 字段编码（小驼峰）
  "name": "名称",                    // 中文名
  "desc": "名称",
  "type": "base",                    // base=普通 / system=系统
  "dataType": "varchar",             // 物理类型
  "dataTypeNew": "varchar",          // 逻辑类型（重要）
  "attrLength": 255,
  "precision": null,
  "defValue": null,
  "format": null,
  "isNull": "Y",
  "isIndex": "N",
  "sn": 1,                           // 序号
  "objectType": null,                // 关联对象（object/dic 时）
  "options": {"isMultiple": false, "isDefault": false},
  "fieldName": "name_",              // 物理列名（带尾下划线）
  "extraData": {"selectOptions": [], "relationship": null}
}
```

### 关键对照结论

1. **物理列名规则**：`code` 小驼峰 → snake_case + 尾下划线。
   `processDefId` → `process_def_id_`，`nameEn` → `name_en_`。
   ✅ 与 pp6kit 的 `camel_to_snake + "_"` 完全一致。

2. **系统字段是显式的**：真实系统里 `id / tenantId / ip / createBy / createTime /
   updateBy / updateTime / deleted / version / processNode / processHandler /
   processDefId / processInstanceId` 都是 attrs 里的真实条目，带 sn 序号。
   ✅ 与 pp6kit 的「系统字段补齐」逻辑一致，但**注意**：
   真实系统还多了 `processNode / processHandler / processDefId / processInstanceId`
   这 4 个流程相关字段，pp6kit 是否补齐这 4 个需要核对（`flow_driven=是` 时）。

3. **dataTypeNew 类型**：真实系统用 `varchar / user / datetime / number / ...`，
   和 pp6kit 的 `fieldtypes.json` 命名一致。


### 7.4 关键发现：field_options 的「精简版 vs 完整版」

数据库存的 `field_options_` 是**精简版**（只存用户改过的值），
网页返回的是**完整版**（含前端默认值）。

| 控件 | 数据库精简版 | 网页完整版 |
|---|---|---|
| number | 15 键 | 31 键 |
| text | （工具 13 键） | 28 键 |

**结论**：导入系统只需精简版，系统会自动补前端默认值。
工具现有骨架（text 13 键）正是精简版，所以补充骨架也用数据库的精简版即可。

## 九、表单布局的真实嵌套结构（2026-10-28 深挖）

### 9.1 整体结构

表单字段是**树形结构**，靠 `parentId` 挂在父节点下（数据库 `iform_form_field.parent_id_`
和 XML `<formField parentId="...">` 一致）。

```
formField (grid, label="新建表单页面")          ← 根容器
├── formField (hidden) 主键
├── formField (hidden) 版本
├── formField (hidden) 拼音
├── formField (grid, label="栅格布局")  sn=1     ← 每行一个 grid
│     └── column span=24 → [供应商名称]
└── formField (grid, label="栅格布局")  sn=2
      └── column span=24 → [编号, 统一信用代码]
```

### 9.2 两处重要差异（工具目前不准）

**① sn 是「每个 parent 内部独立编号」，不是全局递增**

实测数据：

| parent | 子项 sn |
|---|---|
| None（根） | 1, 2, 3, 4 |
| 根 grid | 1, 2, 3, 4, 5, 6 |
| 某行 grid | 1 |
| 另一个 grid | 1, 1 |

工具目前用的是全局连续编号（5,6,7,8…），**不影响导入但不合原样式**。

**② 每行是一个独立 grid，不是一个 grid 装多个 column**

系统真实布局：

| 场景 | columns 数 | span | gutter | justify |
|---|---|---|---|---|
| 整行一个字段 | 1 | 24 | 0 或 70 | start / space-between |
| 两个字段并排 | 2 | 12 | 70 | space-between |

工具目前把所有字段塞进**一个** grid 的一个 column（span=24），
渲染出来会横向挤压。需要在生成时按「行」切分成多个 grid。

### 9.3 字段引用方式（一致 ✓）

grid 的 `columns[].fields` 里放的是**字段 id 字符串数组**：

```json
{"columns":[{"name":null,"label":null,"fields":["1554539219555188738"],"span":24}]}
```

工具也是用 id 引用，这部分一致。

### 9.4 grid 的 fieldOptions 完整键

```
align, clearable, columns, controls, gutter, is_kit, justify,
kit_id, kit_key, mobile, pkKey, responsive, selection, type
```

`type` 固定 `flex`，`kit_key` 在根容器上是 `new`（新建表单）。

### 9.5 待改进

- [ ] 生成时按「行」切分成多个 grid（每行一个），而不是一个 grid 装全部
- [ ] 子项 sn 改成每个 parent 内部独立编号
- [ ] 两列布局时 gutter 用 70、justify 用 space-between

## 十、列表视图配置全解（2026-10-28）

### 10.1 视图类型由 attrs.template_renderview_type 决定

`iform_data_template_tpl.attrs_` 里有个 `template_renderview_type`，值决定视图类型：

| 值 | 视图 | 关键配置键 |

## 十二、本轮修复（2026-10-28）

### 修复：表单布局 grid 切分错误

**问题**：工具把一行里的多个字段塞进**同一个 column**，根 grid 按行数均分 span。

- 7 个字段的 grid → 1 个 column 装 7 个字段（横向挤压）
- 根 grid 7 行 → span=[3,3,3,3,3,3,3]（7 行横向并排）

**修复**（`gen_form.py`）：

1. 行 grid：一行 N 个字段 → **N 个 column**，每列放一个字段
   （两列时骨架自带 span=[12,12] + justify=space-between）
2. 根 grid：**固定 1 个 column、span=24**，把各行 grid id 依次放进去（纵向排列）
3. sn 编号：改成**每个 parent 内部独立编号**
   - 根层：根 grid=1，hidden 字段 2..4,5，行 grid 跟着继续
   - 每行 grid 下的叶子控件：各自从 1 开始

**验证**：
- 生成的 grid 结构：根 cols=1 span=24；行 grid 单字段 cols=1 span=24；
  双字段 cols=2 span=[12,12] space-between —— 与系统实测一致
- 真实 PP6 目录反解再出包：15 个行 grid 是 2 列、12 个是 1 列

## 十五、项目团队的真正表关系（2026-10-28 用户报错后深挖）

### 15.1 用户发现的问题

问「查询项目的项目名称和项目团队成员」，生成的 SQL 只走了
`pp_project → pp_project_member → iform_party_employee`，

### 15.2 真实结构（三层）

```
pp_project
  └─ pp_project_role (project_id_, object_role_id_)        369 行
       角色名不在本表，在 iform_object_role（按 object_role_id_ 关联）
       └─ pp_project_member (project_id_, project_role_id_, user_id_)  49 行
            └─ iform_party_employee (id_) → name_
```

### 15.3 踩坑：project_role_id_ 名不副实

`pp_project_member.project_role_id_` 看起来像指向 `pp_project_role.id_`，实测：

| 指向 | 匹配率 |
|---|---|
| `pp_project_role.id_` | **0 / 49** |
| `pp_classification_project_role.id_` | 0 / 49 |
| `iform_object_role.id_` | **49 / 49** ✅ |

也就是说这一列存的是**角色字典 id**，不是项目角色行 id。
按名字猜关联必错。

### 15.4 角色名字在哪

`iform_object_role`（81 行），`object_type_='project'`，
字段 `name_`（项目发起人/项目总监/APQP项目经理…）、`code_`（ROLE001…）。
这张表不在 pp_ 扫描范围，需要在 `guard.PARTY_TABLES` 里放行。

### 15.5 修复：语义模板

`local.build()` 开头加 `_build_team_template()`，命中「项目 + 团队/成员/角色/人员」时直接出正确 SQL：

| 问法 | 产出 |
|---|---|
| …项目团队成员 | 项目名称 · 项目角色 · 团队成员（LEFT JOIN，空角色也列） |
| 项目有哪些角色 | 项目名称 · 项目角色 |
| 每个项目有多少成员 | 项目名称 · 数量（人去重） |

- 角色要 `JOIN pp_project_role` 且**从角色侧 LEFT JOIN 成员**，这样没配人的角色也会出现

### 16.4 实现：报表语义层

新增 `pp6kit/nlq/reports.py`，`local.build()` 最先调用它。
理由：启发式擅长「列出 XX / 条件是 YY」，但报表问的是**指标 + 阈值判定**，
实测 10 条标准报表问题**全部答错**（答成明细清单或选错表）。

12 个模板：

| 触发 | 产出 |

| 风险矩阵 | 可能性 × 影响 分布 |
| 风险按等级/状态分布 | rating_ / state_ 分组 |

### 16.6 修掉「历史示例抢答」

而相似度按二元组算，「超支的项目有哪些」和「本月创建的项目有哪些」
尾部完全一样，于是被判定相似，套用了后者的 SQL。

修法：新增 `local.match_template(pack, q)`，在 webui 的本地问答里
**先跑报表/团队模板，命中就直接返回**；没命中才去查历史示例。
理由：模板是验证过的确定性 SQL，示例是历史沉淀（可能是早期错答案）。

修复后：

```
超支的项目有哪些     → 项目名称|预算|实际成本|结余|预算执行率%  1 行
项目健康度一页纸     → 11 列 32 行
每个成员的任务负载   → 成员|任务数|已完成|已逾期 32 行
```

## 十七、AI 生成 SQL 的能力提升（2026-10-28，抓公开语料 + A/B 实测）

### 17.1 先看公开语料说了什么

拉了两份公开数据做参照：

| 来源 | 内容 | 结论 |
|---|---|---|
| `taolusi/chisp`（CSpider） | 仓库只有脚本，数据集另行发布 | 拿不到 |

```
窗口函数 0% · CTE 0%
复杂度：0–2 分占 78%
```

**关键结论**：真实问题 78% 是 0–2 分复杂度，结构上（JOIN/COUNT/GROUP BY）
我们的引擎已经覆盖。瓶颈不在 SQL 语法，而在**中文问法 → 本库表列**的对应关系，
这是公开英文语料帮不上的部分。

所以按 Vanna 的思路——**用自己库里已验证的问答对做 few-shot**。

### 17.4 顺带修掉一个真实缺陷

## 十八、用户修正 SQL → 反哺生成能力（2026-10-28）

### 18.1 为什么这条最重要

前面所有增强（198 条内置语料、模板、表加权）都是我们**猜**用户怎么问。
而用户亲手把 SQL 改对的那一刻，是**最真实的监督信号**——
他知道「本月创建的风险」到底该不该只看 High、该不该带状态过滤。

这类数据比任何公开语料都值钱，必须记下来。

### 18.2 交互设计

```
用户提问 → 生成 SQL（占位在可编辑框里）
        → 用户直接改那几行
        → 编辑框一变，"保存修正"按钮自动出现
        → 点保存（会校验 + 试跑，必须能出数据）
        → 下次同样的问题直接用他改的
```

关键细节：
- SQL 框本来就是 `textarea`，不需要额外弹窗
- 前端用 `Q.generatedSql` 记住「机器给的原版」，`input` 事件比较差异，
  只有真的改动了才亮按钮（没改就没必要烦用户）
- **必须先跑通且有数据才入库**：改坏的 SQL（或本来就该 0 行的）不入库，
  避免把错误学进去

### 18.3 三级优先级

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1️⃣ 最高 | **人工修正**（同问句精确匹配） | 人比模板权威，直接覆盖 |
| 2️⃣ | 语义模板（报表/团队） | 验证过的确定性 SQL |
| 3️⃣ | 相似历史示例 | 二元组相似度 ≥ 0.42 就复用 |

近义问法（"本月创建的风险有哪些"）会走第 3 级命中修正版的 SQL，
徽标如实显示「人工修正」，不冒充 AI 或规则。

### 18.4 顺带进 few-shot

修正条目在 `pick_examples` 里 **+0.5 加权**（问句相似度满分才 1.0），
所以走 AI 路径时也会优先拿修正案例当参考——不只是同句，相近的问法也能借到写法。

### 18.5 数据结构

```json
// ~/.pp6kit/nlq.json
{"question": "查一下高等级风险",
 "sql": "SELECT ... AND rating_='High' AND state_<>'closed' ...",
 "source": "corrected",
 "original_sql": "机器原来给的那条",
 "corrected_at": "2026-10-28T13:05:00"}
```

存 `original_sql` 是为了将来能分析「我们常在哪类地方改错」。

### 18.6 实测

```
① 查一下高等级风险        规则生成    86 行
② 用户改成「High 且未关闭」 → 保存成功 85 行
③ 再问同句                人工修正    85 行  ← 用了改后的列（风险名称/等级/状态）
④ 问"查一下高等级风险有哪些"  人工修正    85 行  ← 近义也沾光
```

护栏实测：先试存一条 0 行的 SQL，被拒并提示
"这条 SQL 能执行但返回 0 行，没有记录"。

### 18.7 补记：修正是为了什么（备注）

只存 SQL 有个问题：半年后回看「为什么这条规则要看未关闭」没人答得上来。

所以改成框下带一行备注：

```
┌ 用户改完 SQL 后自动出现 ─────────────────────────┐
│ [为什么这么改？（可选，比如「我们只看未关闭的」）]  [保存修正] │
└──────────────────────────────────────────────┘
```

- 存进 `examples[].note`，截断 200 字
- 复用这条修正时，SQL 卡片标题后面会显示 `来自：<问题>　✎ <备注>`
- 返回体里也带 `note` 字段，接口调用方能拿到

实测：

```
① 看看高等级风险          规则生成 86 行
② 保存（备注：我们只关心未关闭的高风险…）→ ok
③ 再问同句                人工修正 86 行 | 带回备注 ✓
④ 问"看看高等级风险有哪些"   人工修正 | 带回备注 ✓
```

这样「库里为什么有这条怪规则」永远能追到人话解释。

## 十九、非标准 Excel → 标准模板（2026-10-28）

### 19.1 需求

项目经理手上往往已经有一份自己整理的表（列名、示例、枚举值都在里面），
比任何一句话描述都准。所以加了这条路：

```
传自己的 Excel → AI 读表并映射成标准对象 → 预览可改 → 下载标准 Excel
```

和「一句话生成」的区别只在**需求从哪来**；后半段（表单/列表设计、套模板出包）
完全复用，保证两条路产物一致。

### 19.2 关键实现：怎么把表喂给模型

不把整张表塞进去（几十列 × 几百行会撑爆上下文，也没必要）。压成概要：

```
【表 设备台账】约 5 行，9 列
  - 设备名称｜样例：三坐标测量仪、回流焊炉、老化测试柜｜5 种取值
  - 所属项目｜样例：星澜MCU项目、昊驰电驱项目、晶圆厂封装线｜3 种取值
  - 状态｜样例：在用、维修中、闲置｜3 种取值
  ...
```

判断字段类型只需要**列名 + 3~6 个样例值 + 取值种数**，这些就够。

### 19.3 踩坑：表头不是第一行

项目经理做的表经常这样：

```
第 1 行：XX公司 设备台账（2026版）      ← 大标题，只有 1 个格子
第 2 行：（空）
第 3 行：序号 | 设备名称 | 设备编号 ...  ← 真表头，9 个格子
```

按「第一行」取表头会得到一列名为「XX公司 设备台账（2026版）」的假字段。

改法：**前 8 行里挑非空单元格最多的那行当表头**。标题行只有 1 个格子，
自然被跳过；真表头一挑就准。

### 19.4 预览改成可编辑

原来预览是只读表格，现在每个字段一行可改：

| 列 | 控件 |
|---|---|
| 字段名称 | 文本框 |
| 编码 / 物理列名 | 只读（改动风险大，交给规范生成） |
| 类型 | **下拉**（10 种，用**字段层**叫法：单行文本/数字/日期控件/选项/下拉框…） |
| 长度 | 数字框 |
| 关联 / 选项 | 文本框；`dic` 类型这里填的是**候选值，逗号分隔** |
| 操作 | × 删掉这个字段 |

改完点「套用并下载 Excel」，下载的就是改后的版本（前端直接改 `state.aiData`）。

### 19.5 顺带修掉两个真 bug

**① `dic` 类型被误降级成文本**

`build_bo` 原来把 `object` 和 `dic` 一起判：「没说关联对象就降级」。
但选项字段的字典 key 可以按字段编码自动生成（模板说明里就是这么写的），
不该降级。结果「状态」这种明显的枚举列被丢成文本、候选值也丢了。

改成：`dic` 缺 key 时用字段编码兜底；只有 `object` 才降级。

**② 删字段后表单/列表还引用它**

在预览里删掉「序号」后导出，check 报：
`控件 serialNumber 在对象字段中不存在，可能无法保存数据`。

修法：`ai_apply_bo` 里拿 `valid = {字段编码}`，
构建表单时跳过不在其中的控件（容器类除外），列表的列/排序/标题字段同样过滤。

### 19.6 实测

输入（故意做乱：标题行 + 空行 + 9 列杂项）：

```
设备台账
序号 | 设备名称 | 设备编号 | 所属项目 | 负责人 | 购置日期 | 原值(元) | 状态 | 备注
```

AI 输出（glm-4-flash，约 16s）：

```
对象 设备台账 / equipment_ledger          表 pp_equipment_ledger
设备名称     varchar      设备编号  varchar
所属项目     object      负责人    user
购置日期     datetime     原值(元)  number
状态         dic          在用/维修中/闲置      ← 候选值自动提取
备注         clob
```

预览里改三处（所属项目→对象、状态补「已报废」、删掉序号）后导出：

```
读取概况: 业务对象=1  字段=8  表单=1  表单控件=8  列表=1
结果: 0 个错误, 1 个警告（status 是数据库关键字，建议改名）
```

表单控件数与字段数一致，说明删字段后引用也被清理了。

## 二十、关联对象（object 字段）到底怎么接（2026-10-28 用户追问）

### 20.1 问题

「我的合同里有个项目字段，这个项目要选的是业务对象『项目』」。

原来的做法有两个洞：

| 环节 | 原来 | 后果 |
|---|---|---|
| AI 提示词 | 只说「objectType 填对象编码」 | 模型自己编（`Project` / `项目` / `pp_project`） |
| `known_objects` | webui 里写死成 `[]` | 模型根本不知道系统里有哪些对象 |
| 校验 | 只查「非空」 | 填错照样过，导入后是**空下拉框** |
| 表单控件 | 取值来源在预览往返时丢了 | 控件没数据源，甚至残留示例值 |

### 20.2 对象清单从哪来：查库，查不到用快照

新增 `pp6kit/objects.py`：

```
目标库 iform_bo_def（187 个对象） → ~/.pp6kit/objects.json（缓存 12 小时）
                                   ↓ 连不上
                          assets/objects.json（随包快照，10KB）
```

- 接了数据库：后台线程拉一次（不阻塞「生成」按钮），12 小时过期
- 没接数据库：用随包快照，仍然是**真实编码**，不是猜的
- 手工刷新：`POST /api/objects/refresh`；`GET /api/objects` 看当前来源和条数

实测本库里的关键对象：

```
project   项目        customer  客户        contract  合同
product   产品        classification 项目类型   contract_payment 合同收付款记录
```

注意员工不在这套对象里（是平台表 `iform_party_employee`），
所以「负责人」应该用 `user` 类型，不是 object。

### 20.3 三层归一：Project / 项目 / pp_project → project

`objects.resolve()` 依次试：编码精确 → 名称精确 → 名称互相包含。
「项目」「项目表」「所属项目」「pp_project」「Project」全部归一到 `project`。

`build_bo` 里对 object 字段做归一，并把过程写进提示：

```
字段「所属项目」的关联对象 项目 → project（项目）        ← 归一成功
字段「关联设备」关联的对象 equipment_nonexist 在系统对象清单里找不到…  ← 归一失败
```

### 20.4 提示词：给清单，并且只准用清单里的编码

按表头挑相关候选（`objects.rank`），其余对象只报编码，控制 token：

```
【本系统已有的业务对象】
object 类型的 objectType 只能填下面出现过的编码，不要自造、不要填中文名：
和本表列名相关的候选：
- contract｜合同
- customer｜客户
- project｜项目
其余可用编码：DR NEW01 TR1 TR2 action_item approval ...
```

排序要点：**只认「表头里含对象名」**（所属项目 ⊃ 项目）。
反过来（对象名里含表头）只给弱分，否则「项目类型项目状态参数配置」会靠堆字排第一。

### 20.5 兜底：列名等于对象名就改成关联

实测 glm-4-flash 看到样例是「江城晶圆制造基地」就把「客户」判成 varchar，
哪怕列名就是「客户」，提示词写了两遍也不听。

所以加了确定性规则 `_upgrade_objects()`：列名**完全等于**某个对象名（或去掉
「所属/关联/对应」前缀后相等）且当前是文本 → 改成 object。带「名称/编号/单号/
备注/说明/描述」的不动，避免把「合同名称」判成关联「合同」。

### 20.6 预览：关联对象是下拉，不是输入框

- `选项`（dic）：仍是文本框，填候选值
- `关联对象`（object）：改成 `<select>`，option 文本 `project｜项目`，
  187 个对象全给；当前值不在清单里时，补一个 `⚠ xxx（对象库中不存在）` 并整行标黄
- 卡片头部显示 `对象库 187 个 · 目标库`，让人知道候选是哪来的

### 20.7 顺手修掉两个真 bug

**① 表单控件「取值来源」在预览往返时被吃掉**

`ai_form.to_dict()` 的 `fields` 列表漏了 `valueSource`，前端拿不到，
导出 Excel 时这一列就是空的 → check 警告「下拉类控件未填取值来源」。

修：`to_dict` 两处（rows / fields）都带上；`ai_apply_bo` 再用字段本身的
`object_type` 兜底（object → 对象编码，dic → 字典 key）。

**② 空来源会残留骨架里的示例数据源**

`gen_form._apply_options` 原来只在有值时覆盖，没值就留着 snippet 骨架里的
`value_source: project_grade_value`。也就是说：一个没配来源的「所属项目」下拉，
导入后点开列出来的是**项目级别**——能选，但选的是错的东西，比空下拉更难发现。

修：无来源时 `pop` 掉 `value_source` 并把 `datasource` 清空。

### 20.8 实测（合同台账.xlsx）

输入列：合同名称 / 客户 / 所属项目 / 合同金额 / 签约日期 / 收款进度 / 负责人 / 状态

```
合同名称   varchar
客户       object  customer      ← AI 判成文本，被确定性规则纠正
所属项目   object  project
合同金额   number
签约日期   datetime
收款进度   number
负责人     user
状态       dic     status
```

导出 Excel `2_字段`：「客户」「所属项目」两行数据类型 = 下拉框，关联对象 = customer / project。

出包后核对 XML：

```
<attribute code="project" dataTypeNew="object" objectType="project" .../>
<formField name="project" ... value_source="project" .../>
```

check：`0 个错误, 1 个警告`（只剩 `status` 是数据库关键字的命名提醒）。

### 20.9 新增校验

`validate.py` 里对 object 字段做一次核对：既不在本包对象里、也不在对象目录里
→ 警告「导入后会是空下拉框」。这样外键写错在出包前就能看见，不用等导入后试。

## 二十一、实战：三九蝶变「表单搜集表」跑通（2026-10-28）

用户传了 `PP6/三九蝶变项目表单及流程图搜集表.xlsx`，界面回「不支持」。
这不是格式问题，是**读取器和数据模型都假设错了**。

### 21.1 根因一：WPS 把工作表尺寸写成 A1:A1

```python
wb = load_workbook(data, read_only=True)
ws.calculate_dimension()   # 'A1:A1'
list(ws.iter_rows())       # 只有 1 行（大标题）
```

openpyxl 的 read_only 模式**信任文件里声明的 dimension**，而 WPS / 部分导出工具
把它写成 `A1:A1`。于是 26 张表每张只读到 1 行，汇总结果「0 张有效表格」，
前端就只看到一句报错。

修法：读表前 `ws.reset_dimensions()`，让它按真实内容重扫。

```python
def _read_grid(ws, max_rows=60):
    try:
        ws.reset_dimensions()      # ← 关键
    except Exception:
        pass
```

这一条影响面最大：**所有 WPS 导出的 xlsx 都可能是这个坑**。

### 21.2 根因二：这份文件不是「表头 + 数据」，而是表单规格

26 张表里 19 张是这种结构：

```
第 1 行  三九项目基本信息表单            ← 表单标题
第 2 行  项目基本信息                  ← 分组
第 3 行  项目名称 | 【自动带出】 | 项目编码 | 【自动带出】
第 4 行  项目经理 | 【自动带出】按最新状态更新 | …
第 23 行 一体两翼视图所需               ← 又一个分组
```

原来的 `summarize()` 只会找「非空格子最多的那一行当表头」，
在这张表上会把「项目名称/【自动带出】/项目编码」当成三列表头，
数据行全是说明文字——完全没意义。

### 21.3 新读取器：以【说明】格子为锚点反找标签

```
表单规格判定：整表以【开头的格子 ≥3 个
字段提取：每个【…】格子 → 往左看 3 格 → 没有就往上找 →
          拿到标签，配上【里的控件类型】和后面的补充说明
分组：整行只有一个非空格子（且不是说明）→ 分组标题
```

这样三种排版一次覆盖：

| 排版 | 例子 | 靠哪条规则 |
|---|---|---|
| 标签在左、说明在右 | 项目名称 ｜【自动带出】 | 同行左看 |
| 横向表头、说明在下一行 | 年度目标表的第 2/3 行 | 上行同列 |
| 标签单独一行、说明在下一行开头 | 周报「本周项目执行进展」 | 上行左看 |

同时自动跳过两类干扰：右侧贴着的「序号｜流程节点｜责任角色」流程小表
（没有【标记，不会成为字段）、以及示例数据行（`【项目1里程碑2】每完成一个…`
上一格也是说明，找不到标签）。

### 21.4 控件类型映射（文档说了算）

| 文档标记 | 落成的类型 |
|---|---|
| 【单行文本】【只读文本】【自动带出】【自动识别】 | varchar（后三种同时设为只读） |
| 【多行文本】 | clob |
| 【下拉选择】【下来选择】【单选】 | dic，并把「候选值 A、B、C」拆成选项 |
| 【日期】【日期选择】 | datetime |
| 【项目选择】 | object → project |
| 【成员选择】【人员选择】 | user |
| 【附件上传】 | attachment |
| 写了「候选值」但标记是别的 | **一律 dic**（项目状态就是【自动识别】+ 候选值） |

候选值解析兼容三种写法：`候选值：A、B`、`候选值 A/B/C`、以及不带前缀的纯罗列
（`正常、风险、重大风险`）。带动作的说明（「从PMO角色选择绑定，并可动态更新维护」）
不会被当成选项拆开。WPS 的图标字体私用区字符（`\uf06c`）会被清掉。

### 21.5 文档是准的，模型只是帮忙

`analyze()` 里加了两道**规格优先**的校正：

1. `_merge_spec_fields()`：文档有、模型漏写的字段按拼音补回来
   （`naming.to_english('意向注册分类')` → `yiXiangZhuCeClassification`）。
   39 个字段一次让模型全写对不现实，但文档是准的，不能因为它懒就少字段。
2. `_apply_form_spec()`：类型和候选值以文档为准，覆盖模型的判断。

提示词也补了一节：**「字段类型完全照文档标注，不要自己重判」**，
并把 token 预算从 3000 提到 6000（40~60 个字段会截断）。

### 21.6 一个文件 26 张表 → 让人选

- 默认分析**第一张表单**（原来按「字段最多」挑，会落到 57 个字段的预立项，又慢又不对）
- 返回体带 `formSheets`（26 条清单：名字、类型、字段数）
- 卡片顶部出现下拉：「这个文件里有 26 张表（19 张表单），当前分析的是…」，
  换一张就重新分析（`/api/ai/sheet?sheet=<名字>`）
- 认不出时不再只说「没读到表格」，会说明支持哪两种格式并列出读到的表名

### 21.7 只读字段也带进表单

文档写「自动带出/只读文本」的 35 个字段，表单控件设成 `disabled`。
不这样做的话，导入后 35 个只读展示字段全是可编辑框，业务方一句话就退回来。

### 21.8 实测（第一张：项目基本信息-练慧君）

## 二十二、改回「AI 分析」：程序只转录，不做判断（2026-10-28 用户纠正）

用户明确：**导入自己的东西后，要由 AI 来分析，让 AI 生成需要的格式**，
而不是程序用一堆硬编码规则去猜类型。

### 22.1 撤掉的东西

上一版（二十一）里，`ai_sheet.py` 写了一套「程序判断」：

```
HINT_TYPES  【下拉选择】→ dic、【日期】→ datetime…       ← 删
_hint_choices  正则抠「候选值：A、B、C」                    ← 删
_object_for    「项目选择」→ project                        ← 删
_apply_form_spec  用程序判断的结果覆盖 AI 输出              ← 删
_merge_spec_fields 模型漏写的字段按拼音补回                  ← 删
_upgrade_objects  列名=对象名就自动改 object                 ← 删
```

这套规则等于**绕过了 AI**，和产品定位（接项目经理的 AI 模型做分析）矛盾。

### 22.2 现在的边界

| 谁 | 干什么 |
|---|---|
| 程序 | 只做**结构识别**：哪个格子是字段名、哪个是它的说明、哪个是分组；把 `标签｜【说明原文】` 忠实转录给模型 |
| AI | 判断类型、拆候选值、定关联对象、判断只读，输出标准 JSON |

`_extract_form()` 现在只产出 `{label, note, section}`，note 是原始说明原文；
`render_summary` 直接贴原文（`项目名称｜【自动带出】`），不再预解码。
AI 的 JSON 是唯一权威，程序只在 `build_bo` 里把 `Project/项目/pp_project`
归一成真实编码（这是编码纠正，不是「分析」）。

### 22.3 为此把格式扩了一格

让 AI 能表达「只读」：

```
BoField.readonly 新增
ai_bo 的 JSON schema 里字段加 "readonly": false
ai_bo.build_bo / to_dict 透传
ai_form.build_form 读 bo 字段的 readonly → FormField.readonly → disabled
```

### 22.4 提示词是「格式说明书」

AI 拿到的不再是程序判断好的结果，而是一份说明，告诉它每个标记该映射成什么：

```
【单行文本】→ varchar；【下拉选择】→ dic 并把候选值写进 values
只要出现「候选值」，不管前面标记是什么都判 dic（项目分级｜【自动带出】候选值 A/B/C/D）
readonly 默认 false，只有写「只读/自动带出/自动识别/自动生成」才设 true
文档里每个字段都要输出，一个都不能少
```

### 22.5 实测（第一张，纯 AI）

```
对象   项目基本信息  39 字段（AI 自己输全，没用任何补漏规则）
类型   varchar 28 · dic 3 · number 3 · user 2 · datetime 2 · clob 1
候选   项目分级 A/B/C/D
       项目状态 立项中/待启动/在研/暂缓/获批/结题中/已结题/终止中
       项目健康度 正常/风险/重大风险/拟终止
只读   36 个（和文档「自动带出/只读文本」数量一致）
check  0 错误 0 警告；probe 202/202；selftest 7/7
```

结论：判断权交回 AI 后，类型、候选值、只读依然正确——
因为提示词把「标记→类型」的映射写清楚了，模型照做即可。

## 二十三、导入是「更新还是新增」：id 与模板 key（2026-10-28 用户提供关键信息）

用户提供两条平台事实：

1. 导入 zip 时判断「更新还是新增业务对象」看的是 **`iform_bo_def.id`**
2. 表单、列表判断靠 **模板 key**

所以：**用户填的名字如果系统里已经存在，生成的 zip 必须直接写回原有的 id / key。**

### 23.1 先确认数据（实测，不是猜的）

```
iform_bo_def      id_ code_ name_ module_id_       项目 project 项目 1489649312991281152
iform_form_def    key_ 唯一（375 条），有 id_
iform_data_template_def  key_ 唯一（419 条），有 bo_code_ / bo_id_
module_config     id（注意：不是 id_）module_name
```

`module_config.id` 和 bo XML 里的 `moduleId` 完全对得上（项目 = 1489649312991281152）。
列表模板的 `bo_id_` 只有 10/419 有值，但 `bo_code_` 可信，所以归属按 code 认。

### 23.2 登记表：objects.json + templates.json

`objects.refresh()` 现在一次拉四样：

```
iform_bo_def          → code / name / id / moduleId
iform_form_def        → 模板 key → id
iform_data_template_def → 模板 key → id + 绑的 bo_code
module_config         → 模块名 → id
```

表单/列表按 `key == code` 或 `key` 以 `code_` 开头归到对象名下，
存进 `~/.pp6kit/objects.json`；模板和模块存 `~/.pp6kit/templates.json`。
每段查询独立 try，某张表不存在不影响其他（老版本没 module_config）。

实测：187 个对象、375 张表单、419 个列表、28 个模块。

### 23.3 出标识：三道口子

**① 对象 → exist_id**

`objects.lookup(名字)` **只认精确命中**：编码相等（含 `pp_project` → `project` 归一）
或名称相等。找到就把 `iform_bo_def.id_` 写进 `Bo.exist_id`。

**这里踩了个坑，很危险**：一开始复用了 `resolve()` 的「名称互相包含」匹配，
结果「项目绩效看板」包含「项目」，直接被绑到 project 的 id 上——
导入时会把真实的项目对象**覆盖**掉。这比多建一个对象严重得多。
所以 lookup 单独实现，只做精确匹配。「设备台账」≠「设备」，也照样新建。

**② 表单/列表 → exist_key**

`form.key` / `list.key` 在登记表里存在，就记下原模板 id，
`gen_form` / `gen_tpl` 直接用这个 id 生成 XML（导入按更新，不会又建一份同名表单）。

**③ 模块 → module_id**

用户可能直接填「项目」这种模块名，`bind()` 会换成 `module_config.id`。

### 23.4 代码位置

| 文件 | 改动 |
|---|---|
| `objects.py` | `refresh()` 拉四张表；`lookup()` 精确匹配；`find_form/find_list/find_module`；`bind(project)` |
| `model.py` | `Bo.exist_id`、`Form.exist_key`、`ListDef.exist_key` |
| `builder.py` | 出包前调 `objects.bind()`；`bo_ids` 优先用 `exist_id` |
| `gen_form.py` | `form_id = form.exist_key or new_id()` |
| `gen_tpl.py` | `tpl_id = listdef.exist_key or new_id()` |
| `spec.py` / `reader.py` | 业务对象表加「已有对象ID」列（自动填，可手改） |
| `webui.py` | `GET /api/objects/lookup?name=`；AI 响应带 `existObject` |

### 23.5 界面上要看得见

AI 分析结果卡片头部多一枚标签：


## 二十四、一个 zip 装多个模块（2026-10-28 开发确认）

用户去问了开发：**平台支持一次导入多个模块，不只业务对象**。
样例目录里正好有系统自己导出的 `PP6/业务对象/多个对象整体导出.zip`，一看就明白。

### 24.1 系统导出的整包长这样

```
bo/001-test_case_base_category.xml
bo/002-sjzcscd.xml
bo/003-pp_equipment.xml
form/004-project_create_start.xml
data_template/005-customer_list.xml      ← 序号跨目录连续
```

要点：
- 按**目录**区分模块（`bo/` `form/` `data_template/`）
- 序号**跨目录连续**（001…005），不是每个目录各自从 001 起
- XML 内容与单模块包**完全一致**（同样的 `<tns:bodefs>` / `<form>` / `<dataTemplate>`）

也就是说之前 `modules.py` 开头写的「zip 不能混传」是错的，已改正。

### 24.2 实现：多一个「整包」交付形式

`builder._pack_all()`：按导入顺序把各模块 XML 写进一个 zip，重新连续编号。

```
order = {bo:10, dataset:20, filter:20, form:30, list:40}
entry = f"{folder}/{sn:03d}-{basename}"      # 去掉原来的 001- 重新编
```

顺序沿用系统要求的「业务对象最先」——表单和列表都要按表名找对象。
**流程仍然排除在外**：它是裸 XML，走「流程设计」另一个导入入口。

交付物从 4 个变成 5 个：

```
业务对象       001-业务对象.zip
数据集         001-数据集.zip
表单           001-表单.zip
列表           001-列表.zip
整包（全部模块）001-整包（全部模块）.zip     ← 新增
```

### 24.3 报告里写清两种用法

导出的 zip 里 `按模块导入顺序.txt` 改成：

```
两种导入方式，选一种即可：

【方式一 · 一把导入】用「整包（全部模块）」这一个文件，
  里面的 bo/ form/ data_template/ 会一起导入，不用逐个菜单点。

【方式二 · 按模块导入】模块各自成包，按下面顺序逐个菜单导入；
  适合只想更新某一块、或整包导入报错时排查问题。
```

外层 zip 里除 `整包（全部模块）/` 目录外，还单独放一份不带文件夹的整包，方便直接拖进系统。

### 24.4 实测

```
出包（填写模板）  5 个交付物，整包 10607 B
解包核对         bo/001-demo_purchase.xml
                data_template/002-demo_urgency_value.xml
                form/003-create_demo_purchase.xml
                data_template/004-demo_purchase_list.xml
校验             4 个 XML 全部可解析，39 个 id 跨文件零重复
目录名/命名     与系统「多个对象整体导出.zip」完全一致
```

`probe 202/202`；`selftest` 里「重新出包」从 16 个 zip 变成 17 个（多了整包），其余不变。

### 24.5 一个观察到的问题（未改，先记录）

用系统那个多对象包反解再出包，会卡在：

```
✗ [表单 project_create_start] 绑定的对象 project_create 不存在
```

原因是那个表单绑在 `project_create` 对象上，而整包导出时**没把 `project_create` 一起导出来**
（只导了 test_case_base_category / sjzcscd / pp_equipment）。
这是系统导出的包本身不自洽，不是我们的问题；但校验直接中止会导致这份包没法再生成。
后面可以考虑：表单绑定的对象不在包内时，给「跳过该表单」而不是整体中止。

## 二十五、字段编码全面改用拼音（2026-10-28 用户决定）

### 25.1 为什么改

原来的 `to_english()` 是「查英文词典 + 缺词退拼音」的混排方案，导致同一批字段编码
中英混杂、长度不可控：

```
项目名称      → projectName              （词典命中，英文）
MAH持有人     → chiYouRen                （词典没命中，前缀 MAH 整个丢了）
战略类别      → zhanLveCategory          （半中半英）
立项申请单位   → liXiangApplyFormWei      （"申请单→applyForm" 把"单位"吞了）
```

同一个概念在不同人手里会写成 `projectName` 和 `xiangMuMingCheng` 两种，后期对不上。
统一拼音至少规则唯一、可预测、不会因为词典缺词而突变。

### 25.2 现在的规则

```
中文       → 拼音小驼峰（字段编码）
中英混排   → 中文段拼音 + 英文段原样保留
括号补充   → 整段丢弃
超长       → 在词边界截到 32 字符
```

实例：

```
项目名称      xiangMuMingCheng      xiang_mu_ming_cheng_
MAH持有人     MAHChiYouRen          mah_chi_you_ren_
是否多规格     shiFouDuoGuiGe        shi_fou_duo_gui_ge_
汇报PPT       huiBaoPPT             hui_bao_ppt_
项目总预算（含税：万元） → xiangMuZongYuSuan   （括号整段丢）
预算计划（根据计划完成年度日期…） → yuSuanJiHua （括号整段丢）
```

### 25.3 顺手修掉三个坑

**① 中英混排丢前缀**：`MAH持有人` 曾变成 `chiYouRen`（MAH 没了）。

## 二十六、选项字段的两条硬规则（2026-10-28 用户明确）

### 26.1 规则一：没写专用控件，就一律是选项

用户原话：**「当没有明确是实际的部门选择或者人员选择等控件时，都默认是选项」**

所以 `项目需求单位`、`立项申请单位`、`项目研发部门`、`项目资金来源`、

```
「人员选择 / 成员选择」→ user
「项目选择」          → object（objectType=project）
```

这条已写进 `SHEET_EXTRA` 提示词，作为硬规则固定下来。

### 26.2 规则二：候选值必须完整，不能截断


而且 `项目研发部门` 列了 37 个公司名、900 多字，几乎全被砍掉。

改成：**带「候选值」字样的单元格整段保留**（上限放宽到 1200 字），
普通说明才截 48 字。

### 26.3 排查过程中的一个来回

中途试过把换行转成「、」，想让 AI 更好拆候选值——结果 AI 全拆不出来了
（26 个选项字段全部 0 个候选值）。已回退，换行仍转空格。

## 二十七、字段类型只有「选项」，没有「数据字典」（2026-10-28 再纠正）

### 27.1 用户两次追问

> 「可是字段类型没有数据集和字典的选项啊！！！」
> 「怎么生成的预览类型还是显示数据字典 你要严格按照我已有的字段类型进行配置呀」

`UI_LABELS["dic"] = "数据字典"` 没动，所以用户看到的还是错的。这是只改了一半。

### 27.2 根因：把**控件层**叫法当成了**字段层**

`chunk-locales-zhcn.js` 里 `fieldTypes.dictionary = 数据字典` 是**表单设计器**

```

varchar 2027 / number 690 / datetime 514 / user 407 / object 225 /
clob 148 / dic 80 / date 38 / autoNumber 30 / department 19 /
file 8 / userGroupCate 2
```
**不存在** `dictionary` / `dataset` 这种"类型"——那是控件层 `value_source` 的取数方式。

### 27.3 修复

| 位置 | 改动 |
|---|---|
| `fieldtypes.UI_LABELS["dic"]` | 数据字典 → **选项** |

| `fieldtypes.resolve()` | 字段层叫法优先；控件层叫法仍认，但归一后一律写字段层 |

| `ai_bo.SYSTEM` | 明确写「没有数据字典/数据集这两种类型」；拿不准 dic 还是 object 时一律 dic |

### 27.4 「项目需求单位」为什么之前判成对象

### 29.3 顺带修掉的一个真 bug：列表/数据集继承了骨架的 typeId 和时间戳

`gen_tpl.py` 里 `def_attrs = dict(def_src)` 直接复制骨架，然后 `setdefault("typeId","")`
——`setdefault` 只在键**不存在**时生效，而骨架里**有** `typeId`，所以旧的
`1374401991849050112`（项目列表的分类节点）被原样写进了每一个新列表。

查库确认 `typeId` 的含义：指向 `iform_cat_type` 里 `category_key_='DATA_TEMPLATE_TYPE'`
（列表）/ `'FORM_TYPE'`（表单）的分类节点，也就是"这张列表挂在哪个模块下"。
空值允许存在（419 个列表有 15 个为空），但**指向错的模块不行**。

同样的问题还有 `createTime/createBy/updateTime/updateBy`——骨架里是 2025-05 的时间，
`updateTime` 甚至是 2026-10-03，原样搬过去新列表会显示成一年前创建。

修法：
- `typeId` 一律取 `listdef.type_id` / `ds.type_id`（默认空），不吃骨架值
- 时间戳保留键（缺了会成结构差异）但换成**当下的时间**，`createBy/updateBy` 置空交给系统填
- `ListDef` 加 `type_id` 字段

改动后结构差异从 6 处回到 3 处（`pp_equipment` 的 length ×2 + `requirement_category`
的 isDraft，都是历史遗留/我们主动补的系统字段）。
`probe 202/202`，`selftest 6/7`。

### 29.4 已补上的：选项字段的单选 / 多选（`isMultiple`）

视频里"实验类型一次只选一种，用单选"是一条必选项，我们之前完全没输出。

查库（`iform_bo_attr`）：80 个 `dic` 字段的 `options_` **全都带 `isMultiple`**，
其中 **32 个是 true**（40%）。规律也很清晰：

| | `isMultiple` | `attr_length_` |
|---|---|---|
| 单选 | `false` | 32 / 50 / 64 / 255 不等 |
| 多选 | `true` | **一律 1000**（逗号分隔存多个 key） |

改动：
- `model.BoField.resolved()`：dic 字段一律补 `isMultiple`（默认 false），
  显式多选时长度自动放宽到 1000
- `webui._field_options()`：前端/AI 把 `isMultiple`、`isIndex` 放在字段顶层，
  生成器只认 `BoField.options`，之前全丢（`options=` 参数根本没传）。
  现在统一收进 options，且 `isMultiple` 只给 dic/user/department 三种类型

验证：
```
实验类型  length=32   isMultiple=False      ← 默认单选
多选测试  length=1000 isMultiple=True       ← 多选，长度自动放宽
靶点      length=50   isMultiple=(无)       ← 字符串不受影响
```
