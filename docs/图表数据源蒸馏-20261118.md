## 一、链路：一张图表的取数路径

```
custom_page                     仪表盘页面（15 个）
  └─ custom_page_widget         卡片（149 个，17 类组件，图表类 133 个）
       └─ config.dataCode       数据源编码（9 种）
            └─ iform_data_template_def   数据模板，key_ = dataCode（407 行）
                 └─ dataset_key_          → iform_data_dataset（177 个数据集）

```

实测 9 个数据源编码**全部落在单表数据集**上：

| dataCode | 数据集 | 表 | 用途 |

## 二、config 里的语义：维度和度量是两件事

`custom_page_widget.config` 是一坨 JSON，扒开看只有几个关键键：

```json
{
  "dataCode": "project_list_chart",        // 数据源
  "labelKey":  {"k": "classification_id_", "n": "隶属的项目类型"},   // 维度（X 轴）
  "groupKey":  {"k": ""},                  // 分组 / 系列
  "breakupKey":{"k": ""},                  // 拆分
  "valueKeys": [{"k": "normal_hours_", "valueType": "sum"}],        // 度量
  "displayType": "RecordValue",            // RecordCount / RecordValue / DistinctCount
  "distinctField": "",
  "topN": 10, "sortType": "none", "sortDirection": "asc",
  "customQueries": {},                     // 二次筛选（规则树）
  "defaultFilterKeys": ["Q^create_by_^SL", "Q^create_time_^D"]
}
```

统计口径全在这几个键里：

| 键 | 语义 | 实测分布（149 张卡） |
|---|---|---|
| `displayType=RecordCount` | 数行数（COUNT） | 124 |
| `displayType=RecordValue` | 对 `valueKeys[].k` 做 `sum` | 15 |
| `displayType=DistinctCount` | 对 `distinctField` 去重计数 | 0 |
| `isGroup + groupKey` | 按第二维拆系列 | 0（这个库里没人用） |

**最关键的一点**：`valueKeys` 把「工时」「金额」这类词从「对象」里拆出来，
变成 `列 + 聚合方法`。所以系统不会把「按项目统计工时」理解成「数记录条数」。
它的默认值也很说明问题——`valueKeys[0]` 的 `k` 是空串但 `valueType` 是 `sum`，
意思是「先声明这是求和度量，列由用户选」。

### 值来源（valueSource）

模板里每个可筛字段除 `dataType` 外还带 `field_type` 和 `queryCondition`：

```
项目类型  classification_id_  varchar  linkdata  in       link=classification_value
项目状态  state_id_           varchar  linkdata  include  link=project_state_values
计划结束  finish_             date     text      between
```

`linkdata` 指向一个 `type_='valueSource'` 的模板（154 个），它回答两件事：
下拉候选从哪来、以及**码值/外键怎么翻成人话**。

## 三、接口契约（从前端 bundle 还原，供对照）

前端三个关键函数（`js/index.*.js`）：

```js
POST /data/template/customPageDataTable          // 取图表数据（PM）
POST /data/template/customPageDataTableExport    // 导出（RY）
POST /data/template/getCustomPageDataTemplate    // 取数据源定义
```

请求体（`_()` 函数拼的）长这样：

```json
{
  "objectId": "...", "objectType": "project", "objectDataScope": "...",
  "parameters": [
    {"key": "response_data",   "value": "{视图定义：datasetKey/unique/display_columns}"},
    {"key": "calculateField",  "value": "[{\"field\":\"normal_hours_\",\"method\":\"Sum\"}]"},
    {"key": "dimension",       "value": "classification_id_"},
    {"key": "group",           "value": "..."},
    {"key": "Q^create_by_^SL", "value": "..."}
  ]
}
```

响应返回行集，同时带 `__uiValues`（前端 `normalizeUiValueResponse` 读它），
也就是**码值→名称是服务端翻译好的**，前端只负责渲染。

> 这条路走的是网关 `/gateway/*`，数据库里 `iform_auth_app_api` 只有登记过的接口
> 才是公开 API，`customPage*` 没登记，所以直接 curl 会 404/405。
> 要复现只能在浏览器里点，正好说明它是「内部接口 + 前端专用」。

## 四、能搬过来的四点

| 系统做法 | 我们的现状（改前） | 处理 |
|---|---|---|
| 维度 / 度量分离，`valueKeys = 列 + sum` | 只有「选表 + 数行」，「工时」被当对象 | ✅ 新增 `nlq/measure.py` |
| 外键/码值查询即翻译（`__uiValues`） | 单值外键已有 join 翻译，码值仍输出英文 | 🟡 部分具备，码值待补 |
| `timeSeriesConfig` + `periodKey` 按月/季分组 | 时间 + 分组只能吃到一个条件 | ✅ 度量模板支持年/季/月/周/日 |
| `pp_dashboard_statistic` 统计缓存（user×date×type×count，周/月） | 每次现算 | ⬜ 未做，列为下一步 |

## 五、实测：同一批问句，改前 / 改后

（对着 8112 只读库跑，`bin/pp6 probe` 之外另跑了一组）

| 问句 | 改前 | 改后 |
|---|---|---|
| 按项目统计工时 | `COUNT(*)` → 数出 7 行「记录条数」 | `SUM(normal_hours_)` 按项目，35/26/17 小时 |
| 按月份统计工时 | 变成「按填报人计数」，完全跑偏 | `DATE_FORMAT(...,'%Y-%m')`，2026-08 103h / 09 1h / 10 32h |
| 工时最多的 5 个人 | 54 行明细，没排序没聚合 | `SUM` + `ORDER BY ... DESC LIMIT 5`，普明 104h |
| 每个项目类型的平均进度 | 直接报「解析不了」 | `AVG(progress_)` by 项目类型，6 行 |
| 按部门统计工时 | — | `SUM` by 组织名 |
| 成本最高的前 3 个项目 | — | `SUM(amount_)` by 项目，LIMIT 3 |

回归：`python tools/regress.py` 462/462 通过；
`bin/pp6 probe` 206 条语料 201 通过（5 条失败的「本月/最近7天」是库里没有
2026-11 的新数据，改动前就是这 5 条）。

## 六、明确没做的（下一步候选）

1. **默认度量**：「每个预算大类汇总」现在仍退化成 `COUNT(*)`。
   系统那边 `valueKeys` 会强制你选度量列；我们没有「维度表自带默认度量」
   的约定，所以这条先留着（要做得先给 `pp_project_budget_domain_sum` 这类表标金额列）。
2. **码值翻译**：`severity_` 仍是 `CRITICAL`、`status_` 仍是 `in_progress`。
   报表模板里是手写 CASE，通用层还没做。可复用 `iform_data_template_def`
   里 `field_options.linkdata` + `valueSource` 模板自动建映射。
3. **统计缓存**：对齐 `pp_dashboard_statistic`（按人/日期/类型/周月存一份），
   适合工作台那种每次进都重算的卡片。
4. **权限范围**：请求带 `objectDataScope`，我们的 SQL 目前不带数据范围。
   直连客户库时这是**权限口径**问题，不只是性能问题，优先级应该更高。

## 七、给下一个改这块的人

- 维度只从白名单取（`measure.DIM_WHITELIST`）。系统那边同理：维度只能选
  数据集声明过的列，不是任意表都能当维度。放开白名单前先跑一遍 probe。
- 计数问句（「有多少 / 几个」）必须**不**进度量模板，否则
  「每个项目有多少预算条目」会变成「预算金额合计」。
- 加新度量：先确认列在库里不是全 NULL。`pp_project.total_cost_` 是全空的，
  实际成本只能走 `pp_project_cost.amount_`——这条已经在 `reports.py` 踩过一次。
