# 问数引擎：选表为什么要改成打分表

> 这份文档记录一次重构的原因和做法。背景是：靠「遇到一条口语就加一个 if」的方式修选表，
> 修到第 14 处时已经变成修一条坏一条。

## 一、原来的问题

`build()` 里散着 14 处 `table = xxx`，每处都是针对某个具体问法的临时补丁：

```
第 613 行  table = candidates[0][1]          # 默认
第 620 行  table = pp_contract                # 「收入」
第 637 行  table = t                          # 别名更长者上位
第 650 行  table = pp_project_budget_item     # 「花在哪」
第 662 行  table = alt                        # 状态条件换表
第 667 行  table = pp_contract                # 「收入」再来一次
第 674 行  table = target                     # 「都有哪些」
第 695 行  table = t2                         # 分组词含对象名
第 733 行  table = exact                      # 「每个X有多少Y」
第 738 行  table = fuzzy_hit
第 798 行  table = pp_project_member          # 「多少人」
...
```

问题不在单条规则对错，而在**它们互相覆盖**：

| 修了什么 | 破坏了什么 |
|---|---|
| 「待办事项」上位 | 「按项目类型统计」被 pp_todo 抢走 |
| 「每个开发任务责任人」 | 「每个项目的预算总额」 |
| 「预算花在哪」 | 「预算清单」 |

每条都是 `if 某个词 in q: table = 某表`，后执行的覆盖先执行的，
新增一条就等于给所有已有问法加了一个新的干扰项。

实测数据：132 条语料，修一条平均破坏 0.8 条旧用例。

## 二、参考的做法

开源 Text-to-SQL 项目的共同点是**不靠规则硬编码选表**：

| 项目 | 探数 | 做法 | 为什么不能直接用 |
|---|---|---|---|
| WrenAI | 17.9k | 语义层（MDL）描述业务概念，模型基于语义层生成 | 需要 LLM，环境无 Key 时跑不起来 |
| DB-GPT | 20.2k | Agent 框架 + 微调模型 | 重型，整套部署 |
| Vanna | 23.8k | RAG 检索相似问答 | **已归档（archived）** |

没有一条能直接拿来兜底「不用大模型」的场景。但 WrenAI 的**结构**值得借：

```
物理表  ←分离→  业务概念（对象/字段/口语/句式）
                      ↓
                 一次打分决策
```

## 三、现在的实现（`pp6kit/nlq/select.py`）

把 14 处改写换成**一张权重表 + 一次决策**：

```python
def _score_table(t, qn, ctx, helpers) -> (score, reasons):
    # 1  对象名命中          +len(name)*8
    # 2  别名命中            +len(alias)*7
    # 3  字段命中            +min(n,4)*4
    # 4  缺具体字段          -10/个
    # 5  有数据 / 空表        +3 / -6，空表再 -20
    # 6  关联表（无 name_）   -12
    # 7  配置表              -15
    # 8  结构奖励（name_+create_time_） +2
    # 9  句式被查询对象      +30（挂在分组对象上再 +12）
    # 10 分组对象只是限定范围 -12
    # 11 状态条件但无可用状态列 -10
    # 12 按X统计Y：X 降权     -14
    # 13 明细表 vs 抬头表     +10 / -8
```

`build()` 里只剩一处 `table = candidates[0][1]`。

### 中文语序的处理

中文问句的**核心在句尾**，句首多是修饰。这是原来的规则完全没考虑的：

| 句式 | 谁是主体 | 处理 |
|---|---|---|
| 每个 X 有多少 Y | Y | Y +30；X -12 |
| 每个 X 的 Y 数 | Y | 同上 |
| X 都有哪些 Y | Y | 同上 |
| 按 X 统计 Y | Y | Y +14；X -14 |

例：

```
每个项目有多少阶段   → pp_project_phase（不是 pp_project）
每个开发迭代的任务数  → pp_dev_task（它挂 dev_sprint_id_，pp_task 不挂）
按项目类型统计项目数  → pp_project（不是 pp_classification）
```

### 否定表达

原来的否定词表只认「排除 / 不要 / 除了」，而且只看条件**前面** 10 个字。
用户实际说的是「筛选的**任务名称不能包含**根任务」——否定词夹在中间，还隔了 5 个字。

现在两个方向都查：条件前 12 字 + 字段名到值之间 8 字。

```
排除 → 排除的    「的」是中文最常见的插入成分
X 不能包含 Y     NEG_INFIX 里补了「不能包含 / 不可包含 / 不能含」
```

### 疑问词不是筛选值

```
「责任人是谁」→ 之前生成 name_ = '谁'，现在识别为问法，不生成条件
```

### 看数据而不是看列名

同一张表上可能有好几个「状态」列：

| 列 | 数据 | 能不能筛 |
|---|---|---|
| `pp_task.state_` | 601 行全是 0 | 不能 |
| `pp_task.schedule_state_` | 598 个 0、3 个 1 | 能 |
| `pp_dev_task.state_` | 1700 行全 NULL | 不能 |

判据用 `filled / distinct`（注解时统计的真实取值），而不是列名像不像。

## 四、大模型路径同步改进

`engine.py` 的两处改动，让「有 Key」时也受益：

**1. schema linking 复用同一套打分**

```
改前：标签包含即命中 → 149 张表里的前 10 张，常把无关表塞进去
改后：select.link_tables → 打分前几名 + 外键目标表 + 多跳中间表
```

**2. 提示词补齐中文规则**

原来只有「外键要子查询、软删除用 IFNULL」这类技术规则，
缺了最关键的业务语义：

```
10. 每个 X 有多少 Y → Y 是主体
13. 否定说法必须生成反向条件（NOT LIKE / <>）
14. 疑问词不是筛选值（「是谁」不要写 name_ = '谁'）
15. 中文省略（「需求」可能是「系统需求」）
```

**3. 按需降级**

`auto` 模式下大模型失败（没 Key / 网络 / 限流）自动回退本地规则，
并在结果里说明原因，不再直接报错。
