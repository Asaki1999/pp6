# 「流程」样本分析：一个流程定义到底由什么构成

分析对象：`PP6/流程/` 下两个文件

| 文件 | 大小 | 是什么 | 从哪来 |
|------|------|--------|--------|
| `项目立项_20261113145550.xml` | 1.35 MB / 8191 行 | 流程定义（`<workflowDefinition>`） | 系统「流程设计 › 导出」 |
| `config-sync-20261113150255.zip` | 74 KB / 3 条 XML | 配置同步包：1 个业务对象 + 2 张表单 | 系统「发布工作区 › 发布 ZIP」 |

两份文件不是并列关系：**XML 是流程本身，zip 是流程赖以存在的业务底座**。流程里每一个引用（业务类型、表单、状态、字段、处理人）都指向 zip 里的东西。只看 XML 是拼不出流程的——这是本次分析最重要的一条。

---

## 一、流程 XML 的七段结构

`workflowDefinition` 只有 7 个直接子元素，但承重完全不对等：

| 段 | 体积 | 占比 | 作用 | 生成时是否必需 |
|---|---|---:|---|---|
| `id` | 48 B | — | 流程定义 id（UUID） | 必需，新建时必须换新 UUID |
| `name` | 20 B | — | 流程名称（= 业务对象名） | 必需 |
| `moduleId` | 43 B | — | 所属模块 id（与业务对象同一个模块 id） | 必需 |
| `categoryId` | 47 B | — | 流程分类 id（**独立于业务对象分类**，不能复用对象 typeId） | 必需 |
| `businessType` | 46 B | — | 绑定的业务对象编码，`project_create` | 必需 |
| `workflowType` | 38 B | — | `normal` | 必需 |
| `titleFormat` | 80 B | — | 待办标题模板 `${name}-${bo.name}-${bo.createBy}-${bo.createTime}` | 必需 |
| `designer` | 568 KB | 42% | 设计器：节点、流转、条件、处理人 | 必需 |
| `layout` | 85 KB | 6% | 画布坐标（JSON 数组，**一版一个**） | 可再算，但缺了设计器打不开 |
| `nodePermissions` | 700 KB | 52% | 每个节点的字段读写权限（JSON 对象，按 activityId 键） | 必需，缺了整个流程所有人只读不了 |

> 后两段是**纯 JSON 文本**（不是 CDATA，也不是子元素），直接塞在标签里。

### 1.1 `designer` 的结构

```
designer
└─ FlowDefinition  DefaultFlowChartVersion="30" Id=<同 id> IsActive="true" Name="项目立项"
   │              ParallelGoBackMode="Self" SendBackHandlerMode="AllHandlers" SendBackMode="Allowed"
   ├─ FlowCharts
   │  └─ FlowChart  IsPublished="true" Version="N"      ← 这个样本里有 30 个！
   │     ├─ NormalActivity / BranchActivity             ← 节点
   │     │  ├─ Transition ...                           ← 出边（每个节点自带自己的出边）
   │     │  └─ Properties                               ← 节点属性（处理人/表单/业务状态/退回）
   │     └─ ...
   └─ Interceptors                                       ← 拦截器，样本里是空标签
```

**30 个 `FlowChart` 是版本历史，不是 30 条流程。** `DefaultFlowChartVersion="30"` 说明只有第 30 版生效，前 29 版是编辑器留下的快照（而且 v1–v10 是 5 节点的旧图，v11 起才换成 13 节点的新图）。生成器只需要输出**一版**，`Version="1"`、`DefaultFlowChartVersion="1"`。

### 1.2 节点（两类型）

| 类型 | 出现次数 | 必填属性 | 有出边 | 有 Properties |
|---|---:|:--:|:--:|:--:|
| `NormalActivity` | 10 | `Id` `Name` `State` `AllowHandover`；审批节点另有 `ExpectHandleDays` | 除终态外都有 | 有 |
| `BranchActivity` | 3 | 只有 `Id` `Name`（**没有 State**） | 必有（≥2 条） | 只有 `ColorCode` |

`State` 四种取值，直接决定节点语义：

| State | 中文节点 | 业务状态 | GoBack | 处理人 |
|---|---|---|---|---|
| `Start` | 申请人 / 开始 | 待发起 `f9cd5a6d` | 无 | 无（发起人自己） |
| `Ongoing` | 各级审批 | 进行中 `d432d037` | 有 | 有 |
| `Passed` | 通过 | 已完成 `78782698` | 无 | 无 |
| `Rejected` | 不通过 | 已失败 `3184e2aa` | 无 | 无 |

### 1.3 流转（`Transition`）

`Transition` 挂在**源节点**里，`Target` 指向目标节点 id。属性：
`AllowAutoTransform` `AutoTransformReferActivityIds` `CommentRequired` `Id` `Inform` `Name` `Order` `Target` `Type="Forward"`，子元素 5 个：
`Condition` / `Countersign` / `NextHandler` / `Properties`。

三条**必须照抄的写法**：

1. **无条件**：`<Condition>True</Condition>`。条件分支则是
   `{"$type":"WorkflowConditionTreeTransitionCondition","conditionJson":"<转义后的 JSON 字符串>"}`
   ——注意是「JSON 里再套一层字符串」，双层转义，写错系统直接不认。
2. **`Order` 决定分支求值顺序**：判断节点的多条出边 `Order` 从 1 递增，`Name` 就是条件的人话描述（如「预算金额<300万」）。
3. **`NextHandler`** 两种：`ActivityHandler`（按节点配置的处理人走）或
   `None;SelectMode=Referenced;AllowSelectWhenNextHandlersEmpty=false;AllowMultiple=true`（提交时必须人工挑下一处理人）。

### 1.4 节点属性（`Properties`）——流程的「业务含量」都在这里

按节点角色，属性集完全不同（样本实测）：

| 属性 | Start | Ongoing | Branch | Passed | Rejected |
|---|:--:|:--:|:--:|:--:|:--:|
| `FormKey` | ✅ 新建表单 | ✅ 详情表单 | — | ✅ | ✅ |
| `BusinessState` | 待发起 | 进行中 | — | 已完成 | 已失败 |
| `Handler` | — | ✅ | — | — | — |
| `GoBackActivityIds` | — | ✅ `[1,2,3]` | — | — | — |
| `GoBackConfig` | — | ✅ `{"name":"退回","commentRequired":{...}}` | — | — | — |
| `ReviewBusinessParams` | — | ✅ | — | — | — |
| `ColorCode` | 7 | 1 | 2 | 3 | 8 |
| `IfShowButtonOfSaveForm` | true | — | — | false | — |

4 个 `*Events` 字段（`BeforeEnterEvents` / `AfterEnterEvents` / `BeforeCompleteEvents` / `AfterCompleteEvents`）在所有审批节点上都是 `[]`，只有「通过」节点挂了两个自动化：
`[{"type":"automation","automationId":"1515378743793680384"}]` —— 这是界面里配的自动化，生成器默认输出 `[]` 即可。

### 1.5 处理人（`Handler`）——唯一一处「生成器自己造不出来」的东西

```
Chain:[{"header":{"label":"","texts":["科研管理负责人"],"ids":["1567950168366514176"],
                 "type":"RoleSelection"},"nexts":[]}];
SelectMode=Referenced;AllowSelectWhenNextHandlersEmpty=false;
AllowSkipWhenNextHandlersEmpty=false;AllowMultiple=true
```

- `type`：`RoleSelection`（角色）或 `UserSelection`（具体人）
- `ids` 是**组织架构里的角色 id / 用户 id**（雪花号），不是名字。名字只用于界面展示。
- 还支持条件处理人：
  `{"$type":"Conditional","unionMultipleEntries":false,"entries":[{name,condition,strategy}],"defaultStrategy":"..."}`
  ——「主责单位负责人」就是按项目类型（中药类 → 周倩 / 化药类 → 张可）分流。

**这就是流程生成必须先有「角色台账」的原因**：`科研管理负责人` 这个名字在任何地方都没有 id 映射，只能从系统里查或由用户提供。

### 1.6 `layout`（画布）

```json
[{"nodeDataArray":[{"activityId":1,"key":-1,"text":"申请人","category":"Start","loc":"-784.1 -325.2"}],
  "linkDataArray":[{"key":-1,"transitionId":1,"text":"提交","points":[...],"from":-1,"to":-2}],
  "version":30}, ...]
```

- 数组里**一版一项**，靠 `version` 字段与 `FlowChart.Version` 对齐（不是靠下标：数组是 v30→v1 倒序，FlowChart 是 v1→v30 正序）。
- `key` 是负数序号（-1、-2…），`from`/`to` 引用的是 `key` 而不是 `activityId`。 `loc` 是 `"x y"` 字符串。
- `points` 是连线拐点。**设计器打开时会重算布局，所以只要坐标合理、能连上即可**——但这意味着我们完全可以程序化生成（分层左右排布）。

### 1.7 `nodePermissions`（节点字段权限）——占了半个文件

```json
{"1": {"button":[], "field":[{...58 项...}], "column":[...], "row":[], "opinion":[]},
 "2": {...}, ...}
```

- 键是 `NormalActivity.Id`（判断节点没有）；值是 5 个数组。
- `field` 里每一项就是**表单控件的镜像**：`name` / `label` / `field_type` / `field_options`（原样复制表单控件参数）+ 四组权限 `hide` / `read` / `edit` / `required`。
- 样本实测规律极其干净：
  - **开始节点**：`edit = BpmRole(NodeTodoHandler,BpmCreator)`（节点待办人 + 流程发起人可改），`read = all`
  - **其余所有节点**：`edit = none`（全部只读），`read = all`
  - 分组容器（`fieldset`）用 `show` 而不是 `hide`
  - 明细表控件（`tableField`）还会在 `column` 里逐列列一遍（样本里只有开始节点有）
- 结论：**这 700 KB 是机械推导出来的，不是人配的。** 只要知道「用哪张表单」+「哪些字段可编辑」，就能 100% 复现。

## 二、跨文件的 6 条依赖（缺一条流程就废）

| 流程里的引用 | 指向 | 样本里的值 | 缺了会怎样 |
|---|---|---|---|
| `businessType` | 业务对象 `code` | `project_create` | 流程挂不上对象，发起入口不出现 |
| `NormalActivity › FormKey` | 表单 `formDef.key` | `project_create_`（新建）/ `project_create_detail_`（审批） | 节点打开是空白页 |
| `BusinessState` | 业务对象 `processState` 字段的选项值 | `f9cd5a6d`=待发起 / `d432d037`=进行中 / `78782698`=已完成 / `3184e2aa`=已失败 | 流程跑完对象状态不变，列表筛不出来 |
| `Handler.ids` | 组织架构角色/用户 id | `1567950168366514176` 等 | 待办没人收 |
| `Condition.rules[].field` | 业务对象字段编码（dic 要带 `(字典key)` 前缀） | `projectTotalBudgetTaxIncluded` | 条件永远不成立，全走默认分支 |
| `nodePermissions.field[]` | 表单控件（`name`/`field_type`/`field_options`） | 58 个控件 | 节点上字段全只读或全消失 |

**注意 `FormKey` 可以指向不存在的表单**：样本开始节点的 `project_create_start` 在 zip 里根本没有这两张表单中的任何一张，流程照样能导。所以这一项是「软依赖」，我们的生成器应当指向真实表单（新建表单给开始节点，详情表单给审批节点）。

**`moduleId` 复用业务对象的模块，`categoryId` 不能复用**：对象 `typeId=1372668616046067712`，流程 `categoryId=1559242949219319808`，完全不同的两棵树。

## 三、我们 app 的四个缺口

对照 `pp6kit` 现状（`modules.py` 里 `workflow` 模块已登记，但 `builder.py` 明确写着「流程不在生成器里做」，`spec.py` 的说明里也写着「流程定义暂不在本工具范围内」）：

| # | 缺口 | 现状 | 影响 |
|---|---|---|---|
| G1 | **完全不生成流程** | `build -m workflow` 只回一句「请在流程设计里导出 XML 后原样上传」 | 用户每次都要去线上手画一遍；画完还得确认表单/状态/字段对不对得上 |
| G2 | **流程对象缺 `processState`** | `PROCESS_FIELDS` 只有 4 个：`processNode/processHandler/processDefId/processInstanceId` | 流程节点的 `BusinessState` 无处可写；原生对象有 8 个流程字段（还缺 `processName` / `processCode`） |
| G3 | **角色 id 无处录入** | 没有任何「角色台账」概念 | `Handler.ids` 只能凭记忆抄雪花号 |
| G4 | **没有流程的反解** | `inspect` 只认 zip / 目录 | 拿到线上流程 XML 无法变成可编辑的表格，只能手抠 XML |

## 四、改进建议（按收益排序）

| 优先级 | 改进 | 说明 |
|---|---|---|
| P0 | 新增 3 张表：`9_流程` / `10_流程节点` / `11_流程流转` | 把 1.35 MB 的 XML 收敛成「一行一节点、一行一流转」，用户只填业务语义（谁审、什么条件），其余全自动 |
| P0 | 新增 `pp6kit/gen_workflow.py` | 按本分析的 7 段结构反向拼装；`nodePermissions` / `layout` / 标题格式由程序推导 |
| P0 | 流程驱动对象自动补 `processState`（待发起/进行中/已完成/已失败） | 并让 `BusinessState` 直接引用这份字典算出来的短码，两头天然一致 |
| P1 | 流转不填时按节点顺序自动串成一条直线 | 用户只填节点就能出包；要分支才去填 `11_流程流转` |
| P1 | 校验：起点唯一、终态至少一个、判断节点 ≥2 条出边、条件字段必须在对象里、处理人为空要报错 | 这些错在线上表现为「流程导不进去」或「待办没人收」，最费时间 |
| P1 | 流程按「裸 XML」单独交付（`{流程名}.xml`） | 与系统入口一致：管理 › 流程设计 › 导入 |
| P2 | `inspect` 支持单独吃流程 XML，反解成 9/10/11 三张表 | 线上已有的流程可以「拆下来改」而不是重画 |
| P2 | 补 `processName` / `processCode` | 原生流程对象有，列表里能直接显示流程名与流程编号 |

**不建议做**：把流程塞进配置同步 zip。系统里流程是独立菜单（`管理 › 流程设计 › 导入`）吃的裸 XML，塞进 `bo/form/data_template` 之外任何目录都会让整包导入报「不支持的同步对象类型」。这也正是 `modules.py` 里 `zipped=False` 的原因。
