# 报表需求拆解 → SQL 能力

> 目的：把项目管理软件里通行的报表**拆成一条条可执行的需求**，
> 每条需求对应一段确定性 SQL，直接变成问答引擎的能力。
> 不是做一个"报表模块"，而是让用户用一句话问出这些指标。

需求来源：
- MS Project 预置报表目录（仪表盘 / 资源 / 成本 / 进度 四组 18 张）
- PMBOK 通行控制指标（进度偏差、EVM、风险矩阵、资源负载）
- 工时（timesheet）与商务合同（contract）在成熟 PM 系统里的标准用法

落地状态说明：
- ✅ **已落地**：SQL 已验证跑通，返回有意义的数据
- ⚠️ **数据不足**：字段存在但全空，或缺少必要维度
- ❌ **不可做**：库里没有对应数据源

---

## 一、项目进度域

| 编号 | 需求（业务问题） | 数据来源 | 状态 |
|---|---|---|---|
| P-01 | 每个项目的计划进度 vs 实际进度差多少 | `pp_project.planned_progress_` / `progress_` | ✅ |
| P-02 | 哪些项目亮红灯 / 黄灯 / 绿灯 | `pp_project.light_description_` 文案匹配 | ✅ |
| P-03 | 里程碑达成情况（已完成/逾期/未排期/进行中） | `pp_task.is_milestone_` + `progress_` + `finish_` | ✅ |
| P-04 | 每个项目的任务完成情况（任务数/已完成/逾期） | `pp_task` 按 project 聚合 | ✅ |
| P-05 | 项目健康度一页纸（进度+灯+任务+风险+问题+成本） | 多表相关子查询 | ✅ |
| P-06 | 关键路径任务 | `pp_task.is_critical_` | ⚠️ 字段有，但值未落地 |
| P-07 | 甘特视图/S曲线（时间轴分布） | 需按周期快照 | ❌ 无历史快照 |

**P-02 的实现要点**：`light_` 是数值（0/3），但 0 同时表示「主计划未发布」和「绿灯」，
不能当枚举用。系统的判定规则被写成了自然语言存进 `light_description_`
（"进度差大于等于红灯阈值：10，亮红灯"），所以**匹配文案**最稳。

**P-05 的实现要点**：必须用相关子查询，不能多表 JOIN。
任务×风险×问题三者 JOIN 会笛卡尔放大，数字会翻几倍——这是 BI 报表最常见的错。

## 二、成本 / 预算域

| 编号 | 需求 | 数据来源 | 状态 |
|---|---|---|---|
| C-01 | 每个项目的预算 vs 实际成本 + 结余 + 执行率 | `pp_project.total_budget_` + `SUM(pp_project_cost.amount_)` | ✅ |
| C-02 | 超支项目清单 | 同上 + `HAVING 实际成本 > 预算` | ✅ |
| C-03 | 成本按科目/财务域构成 | `pp_project_cost.budget_account_id_` / `finance_domain_id_` | ⚠️ 只有 15 条，可做但样本少 |
| C-04 | 现金流（按季度累计） | 需 `pay_date_` + 计划付款节点 | ❌ 计划侧缺失 |
| C-05 | EVM（PV/EV/AC、CPI、SPI、EAC） | 需基线成本快照 | ❌ `total_cost_` 全 NULL |

**C-01 的关键发现**：`pp_project.total_cost_` **全为 NULL**，
实际成本只能从 `pp_project_cost.amount_` 汇总（15 条，合计 464332）。
任何"直接读 total_cost_"的写法都会得到 0。

## 三、资源 / 工时域

| 编号 | 需求 | 数据来源 | 状态 |
|---|---|---|---|
| R-01 | 每个成员的任务负载（任务数/已完成/逾期） | `pp_task.assignee_ids_` + `FIND_IN_SET` | ✅ |
| R-02 | 每个成员的工时合计（+ 待审批数） | `pp_timesheet.normal_hours_` 按 `user_id_` 聚合 | ✅ |
| R-03 | 每个项目的工时合计 + 参与人数 | `pp_timesheet` 按 `project_id_` 聚合 | ✅ |
| R-04 | 待审批工时明细 | `approve_state_ IN ('1','2')` | ✅ |
| R-05 | 工时按对象类型分布（任务/缺陷/需求…） | `pp_timesheet.object_type_` | ✅ |
| R-06 | 工时填报率（应填未填） | 需"应填"基线（工作日历 × 人员） | ❌ 无基线 |
| R-07 | 可计费工时 / 人力成本 / 利用率 | `work_type_`、`salary_cost_`、`attendance_hours_` | ❌ **三个字段全空** |

**R-07 是行业里最常被问的**（billable utilization 是咨询/外包的核心 KPI），
但本库这三列**一条数据都没有**。想上这个指标，得先在工时表单里
启用「工作类型」和「成本单价」，否则做出来全是 0。

**R-02 的实现要点**：工时的 `approve_state_` 是数字码，
枚举来自表单配置：`0 已保存 / 1 待审核 / 2 审核中 / 3 审核通过 / 4 审核不通过`。
报表里必须转成中文，不能直接甩数字。

## 四、商务合同域

| 编号 | 需求 | 数据来源 | 状态 |
|---|---|---|---|
| B-01 | 合同台账（金额/类别/状态/收款进度） | `pp_contract` | ✅ |
| B-02 | 合同收款执行（合同额/已收/未结/进度%） | `total_payment_amount` / `unsettled_amount` / `payment_progress_` | ✅ |
| B-03 | 未结清合同清单 | `unsettled_amount > 0` | ✅ |
| B-04 | 合同按类别/币种/客户汇总 | group by `category_` / `currency_` / `customer_name_` | ✅ |
| B-05 | 发票开具与收款匹配 | `pp_contract_invoice` | ⚠️ 仅 2 条且 `state_`/`invoice_type_` 全空 |
| B-06 | 应收账龄（30/60/90 天） | 需应收计划日期 | ❌ 合同无到期日字段 |
| B-07 | 合同毛利率 | 需合同成本归集 | ❌ 合同与成本未关联 |

**B-01/02 的实现要点**：`state_`、`category_`、`payment_state_` 全是英文码
（`inProgress` / `productContract` / `partiallyPaid`），
报表必须用 CASE 转中文，否则实施看不懂。

```
state_:            inProgress 执行中 / underNegotiation 洽谈中 / paused 暂停 / completed 已完成
category_:         productContract 产品合同 / developmentContract 开发合同 / supportContract 支持合同
payment_state_:    unpaid 未收款 / partiallyPaid 部分收款 / paid 已收清
```

## 八、给实施的话

三类"做不了"要跟客户讲清楚，别硬报数：

1. **可计费工时/利用率**（R-07）：不是技术问题，是**没人填**。
   `work_type_`、`salary_cost_` 三列全空，任何利用率报表都会是 0。
   要上这个指标，先让对方在工时表单里启用「工作类型」和「成本单价」。

2. **EVM**（C-05）：缺基线成本快照。
   EVM 的 PV 需要"基线时刻的预算曲线"，本库 `total_cost_` 全 NULL，
   等于没有成本基线。要做得在保存基线时冻结一份成本快照。

3. **应收账龄 / 合同毛利**（B-06/B-07）：合同表没有到期日和成本归集字段，
   结构性缺失，不是数据没录。

这三条建议写进售前说明，比事后解释为什么报表是空的要省事。
