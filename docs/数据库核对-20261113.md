## 结论一：`processState` 的四个短码是**系统常量**

这是本次最重要的发现，直接改掉了生成器的一个错误假设。

```sql
SELECT d.type_id_, t.type_key_, d.key_, d.name_
FROM iform_cat_dic d JOIN iform_cat_type t ON t.id_ = d.type_id_
WHERE d.name_ IN ('待发起','进行中','已完成','已失败');
```

命中 20+ 个 `*_processState` 字典类型（project_create / risk / requirement / defect /
plan_approval / qjlc / document_flow / TR1 / TR2 / cs / mrd_requirement …），
**每一组的四个 key_ 完全相同**：

| 选项名 | key_ |
|---|---|
| 待发起 | `f9cd5a6d` |
| 进行中 | `d432d037` |
| 已完成 | `78782698` |
| 已失败 | `3184e2aa` |

交叉验证：这两处也用的是同一组值——

- 对象导出 XML `bo/001-project_create.xml` 的 `dictionaryList` 里出现这 4 个码；
- 流程 XML 的 `<BusinessState>` 里出现这 4 个码（v30 那条流程的 6 个节点只用到了
  待发起 / 进行中 / 已完成 三个）。

### 我们原来错在哪

按 `{对象编码}_processState` 做 scope 算 md5：

```
scope=project_create_processState → 待发起 403e6f64 / 进行中 9861c51c …
scope=demo_purchase_processState  → 待发起 7a7dfd6d / 进行中 e21a9938 …
```

每个对象都不一样。**自洽但和全系统不一致**：如果平台里有按状态码过滤的列表视图、
看板、统计 SQL，我们的对象进去就是另一套码，数据会"看不见"。

### 改法

- `model.PROCESS_STATE_CODES` 写死这四个常量；
- `gen_bo._code_for_field()`：`processState` 字段直接取常量，其余字段照旧 md5；
  字典块与条件值换算共用这一个函数，保证对象 XML 与流程 XML 不分叉；
- `gen_workflow.state_codes()` 的兜底路径也返回常量；
- 回归 `WF27` 钉死，谁改回 md5 立刻红。

# 第二轮：四项一起核（2026-11-14 07:20）

## ① 字段类型：线上有 14 种，我们原来缺 2 种、错 1 种

```sql
SELECT column_type_new_, COUNT(*) FROM iform_bo_column GROUP BY column_type_new_;
```

| 线上类型 | 条数 | 我们原来的处理 |
|---|---:|---|
| varchar / number / datetime / clob / user / department / dic / object / table / autoNumber / userGroupCate | 多 | 已有 |
| **date** | 38 | **没有这一档**，会被当成不认识的类型落到 varchar |
| **file** | 8 | 同上 |
| **attachment** | 4 | **错**：按「附件 JSON 存大文本」推断成 `clob` |

用 `SHOW CREATE TABLE` 看真实 DDL 确认：

```
date        →  `jie_shu_` date                       (pp_qjlc)
attachment  →  `eval_report_` varchar(200)           (pp_project_initiation ×4)
file        →  `ping_shen_cai_liao_` varchar(640)    (pp_tr1)
```

**已改**：`assets/fieldtypes.json` 新增 `date`（datatype=date, format=yyyy-MM-dd）、
`file`（datatype=varchar, length=300）；`attachment` 由 clob 改 varchar(200)、
`verified` 置 true。回归 `BO30` 钉住。
（`BO12`「识别不出的类型按字符串落库」原本拿「日期」当反例，现在它已是受支持类型，
改用「九宫格」。）

## ② 表单控件：我们覆盖 21 种，线上出现 30 种

`iform_form_field.field_type_` 的分布（前几）：text 1266 / grid 632 / select 510 /
label 495 / hidden 452 / datePicker 343 / number 290 / textarea 196 / dictionary 183 …

我们的骨架（`assets/snippets.json › fieldOptions`）覆盖 21 种，**缺失的**：
`radio` `switch` `fieldset` `divider` `collapse` `grid` `grid_layout` `toolbar`
`commentList`（+ `hidden` 我们以 `_hidden*` 三个变体实现）。

其中真正影响数据录入的是 **radio / switch / fieldset**；其余是布局容器。

**结论**：已支持的那批控件不用动——骨架里的 `fieldOptions` 是从真实导出直接抓的
JSON 字符串，键集天然与线上一致（抽查 select 36 键、dictionary 28 键、attachment 34 键
均能在线上样本里对上）。要补的是缺的那几种，做法也现成了：直接从
`iform_form_field.field_options_` 取一条真实值做骨架。

## ③ `workflow` 表是**实例**表，不是定义表

```
列：id, business_type, business_id, flow_definition_id, flow_chart_version,
    title, code, activity_ids, activity_names, activity_state, handler_ids …
样本：('risk', 'WF-20261113001', '[风险]测试交付物模板权限-普明', 'normal', 5)
```

- `code` = **`WF-YYYYMMDDNNN` 流水号**（实例编号），不是静态流程编码；
- `business_type` = 对象编码（dev_task 1851 / risk 213 / issue 213 / defect 58 …）；
- `flow_chart_version` = 走的是第几版流程图。

**所以「processName / processCode」在定义侧根本不存在**，一直挂在"未做"清单里的
那一项可以直接划掉——我们的 `workflowDefinition.xml` 不需要这两样。

## ④ 普通选项字段的短码：平台两种风格并存，我们的 md5 可接受

同一个库里：

- `defect_category`：`FUNCTIONAL` / `PERFORMANCE` / `SECURITY` …（语义英文，人写的）
- `processState`：`f9cd5a6d` / `d432d037` …（8 位 hex，平台种子生成的）

说明选项值 key 是**自由字符串**，平台不做格式约束。我们按 md5 生成 8 位 hex，
落在第二种风格里，**不改**——改了会牵动全部既有产物的字典 key、表单引用与隐藏规则，
收益只是"更好看"，不值这个风险。

> 真要让实施同事看得懂，正确做法是在 `7_表单脚本` 之外单独提供"选项值映射表"，
> 而不是换掉 key 的生成算法。
