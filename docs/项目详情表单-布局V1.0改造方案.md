## 一、结论先行

1. **这个表单本身就在用「表格布局 V1.0」（`grid_layout`，控件名 `gridLayout_12tmngj`，标签写死为 `表格布局V1.0`）。**
   所以「推荐使用布局 V1.0」不是换控件，而是**把这个控件用对**：现在只用了一次，
   把 46 个控件平铺成 23 行；正确用法是**一个分区一个表格布局**。
2. 这套写法在库里已有现成样板：`PP6/表单/项目表单包含级联关系，以及隐藏字段的办法.zip`
   （三九项目立项信息表单）就是 `fieldset ×5 + 表格布局V1.0 ×5`，
   每个分区包一个布局控件，一眼能对上。
3. **数据层不用改**：46 个控件在 `crsanjiu` 里全部对得上对象属性、字典、物理列，
   `field_name` 与 `iform_bo_attr_column` 逐条一致（46/46）。
   真正要改的是**布局分组 + 控件形态 + 字段编排**。
4. 改造后：**7 个分区、26 行、46 个控件**，长文本改多行、四挤一的行拆开、
   标签列从 90px 放宽到 118px。

## 二、现状解剖

| 指标 | 现状 |
|---|---|
| 分区（card / fieldset） | **1 个** card「项目信息」 |
| 布局控件 | **1 个** 表格布局V1.0 |

### 找到的 7 个问题

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| ① | 无分区，46 个控件一条长龙 | 只有 1 个 card | 详情页要滚 10 屏以上，找字段靠翻 |
| ② | 第 8 行 4 个 `span=6` | `developmentMode`/`specification`/`specification2_`/`specification3_` 挤一行 | 每格约 1/4 宽，减掉标签后输入框只剩百来像素 |

| ④ | 语义错位 | 「项目总目标 ↔ 项目批复预算」同行；「研发周期 ↔ 年度目标」同行 | 阅读时上下文串味 |

| ⑥ | 46 个控件 `required` 全是 `false` | 含「项目名称」 | 编辑态可以存空名字 |
| ⑦ | 标签列 90px 装不下长标签 | `labelWidth=90`；「是否工艺技术类项目」9 字、「项目主责单位（项目立项单位）」13 字 | 标签被截断成「是否工艺技术类…」 |

## 四、布局 V1.0 的写法（从真实包里反推）

### 4.1 容器链

```
formDef
└── card / fieldset            ← 分区（card 可挂工具栏按钮）
    └── grid_layout            ← 「表格布局V1.0」，每区恰好一个
        └── 控件
```

- `PP6/表单/项目表单包含级联关系…zip`（立项表单）：`fieldset ×5`，每区一个 `grid_layout`，`border_style:"none"`、`position:"left"`、首个不加 `top_margin`、其余 `top_margin:20`。
- 本表单原有 `card` 上挂着「删除项目」工具栏（`fieldOptions.extra`），改造后**保留在第一分区**。

### 4.2 一个布局控件要写两份，必须同步

| 键 | 内容 | 谁在读 |
|---|---|---|
| `columns` | 扁平单元格清单：`{name:null, label:"单元格", fields:[控件id], span:12/24}` | 设计器栅格 |
| `rows` | 行 → 单元格 → **内嵌完整控件 JSON**（`field_type/name/label/icon/field_options/field_name`） | 运行时渲染 |

`rows[].columns[].id` 就是控件 JSON 里 `parentId` 指向的单元格 id，两边必须一致；
`columns[].fields[0]` 指向 `formField` 元素的 `id`。三处对不上，导入后就是空白或错位。

### 4.3 硬约束

- 栅格 **24 制**：`12` 半宽、`24` 整行；**不要用 6**（四列会被压扁，就是现状问题②）。
- 行 id / 单元格 id 7 位小写十六进制；控件 id 19 位雪花号。
- 同一布局下 `formField.sn` 从 1 连续编号，`card.sn` 接在 hidden 之后（3、4、5…）。

## 六、字段级改造明细

### 6.1 单行 `text` → 多行 `textarea`（7 个）

库里都是 `longtext`，控件却按单行渲染：

| 控件 | 标签 | 库类型 | 处理 |
|---|---|---|---|
| `indication` | 适应症 | longtext | textarea，整行 |
| `specification` | 规格 | longtext | textarea，半宽 |
| `specification2_` | 规格2 | longtext | textarea，半宽 |
| `specification3_` | 规格3 | longtext | textarea，半宽 |
| `targetMechanism` | 靶点/机制 | longtext | textarea，整行 |
| `projectOverallGoal` | 项目总目标 | longtext | textarea，整行 |
| `annualTarget` | 年度目标 | varchar(1000) | textarea，整行 |

改法（对齐样本里 `projectOverview` 的 textarea）：`field_type:"textarea"`、`icon:"Texts"`、
`dbFieldType:"bigContent"`、`rows:5`。`projectOverview` 原本就是 `editor`（富文本），保持不动。

### 6.2 其它

| 项 | 改动 | 理由 |
|---|---|---|
| 必填 | `name`（项目名称）→ `required:"true"` | 其余 45 个仍非必填，避免详情页编辑被卡住 |
| 标签列 | `labelWidth` 90 → **118** | 「是否工艺技术类项目」9 字、「营销承接部门」6 字不再截断 |
| 标签收短 | 「项目主责单位（项目立项单位）」→「项目主责单位」 | 括号内是同义重复，90px 下必截断 |
| 标签收短 | 「技术转让费（含税：万元）」→「技术转让费（含税）」 | 单位改用后缀表达 |
| 标签收短 | 「委托研究费（万元）」→「委托研究费」 | 同上 |
| 金额单位 | 批复预算 / 技术转让费 / 委托研究费 / 预算已支出 → `units:"万元"` | 标签里不写单位，输入框右侧带「万元」，与「执行率」带「%」一致 |

**没动的**：`formDef` 的 `script`（4681 字符的 beforeLoad，含「获取项目信息」规则引擎调用）、
`formRules`（9 条，变更预警状态的赋值规则）、`formRights`（48 条）、`formBo`、
两个 hidden 控件、所有字典与 `boCode` 绑定、控件 id 与 `field_name`。

## 八、导入与回滚

1. 系统 → 表单设计 → 导入 `项目详情表单-布局V1.0.zip`，覆盖 `key=project_summary`。
2. 第一分区**沿用原 `card` 与布局控件的 id**（`card_0rw4o1o` / `gridLayout_12tmngj`），
   其余 6 个分区是新增 id；这样即便有外部配置引用了原容器，也不受影响。
3. 回滚：把原始 `项目详情表单 1.zip` 再导入一次即可（两包同 key，后者覆盖）。
4. 导入后必看三处：设计器里 7 个卡片的栅格预览、第 3 分区 5 个 textarea 的高度、
   第 7 分区富文本是否正常渲染。

## 九、后续建议

- **风险提示列宽**：`project_risk_warning_` 从 `varchar(50)` 扩到 `varchar(255)`（需 DDL，属库侧改动）。
- **二级分区**：若还想再压缩高度，可把「变更与风险」「目标与进展」收进 `tabs`，
  真实系统里有 `grid > tabs > tablelayout` 的写法（见 `项目流程详情表单.zip`），
  但详情页不建议超过 7 个分区。
- **只读化**：若此表单只用于查看，可把 `read_rights` 统一置 `true`、`disabled_rights` 置 `true`，
  编辑交给独立的「编辑表单」，避免详情页误改。
