## 3. 推送工作区（三个入口，实操验证）

## 4. 发布 ZIP（导出同步包）

```
系统管理 → 发布管理 → 发布工作区
  → 全选复选框 (206, 168)（或逐行勾选）
  → 「发布 ZIP」按钮 (1032, 120)
  → 「发布说明」对话框：填说明（写进 zip comment，格式 CONFIG_SYNC_NOTE:<说明>）
  → 点「发布」→ 自动下载 zip 到 ~/Downloads
```

- 下载的文件常卡在 `未确认 NNNNN.crdownload`——**内容已完整**，直接
  `cp "未确认 N.crdownload" 目标.zip` 即可分析
- 发布工作区的条目**不去重**：同一对象推 N 次就有 N 份相同条目（导入端按 id 处理，无影响）
- **变更区 ≠ 必经之路**：设计器推送会直接进发布工作区，不用先攒变更
- 变更区勾选 → 「加入发布工作区」也行，但混着历史测试残留（含删除动作），建议少用

## 6. 浏览器自动化：关键坑与技巧

### 6.1 点击失效的判别（最重要）

| 元素类型 | DOM click | 坐标 click (cua_execute) |
|---|---|---|
| 主文档元素（列表行、勾选框、菜单项、tab） | ✓ 可用 | ✓ 可用 |
| **详情抽屉 / 对话框（portal 渲染）** | ✗ applied 但无效 | **✓ 唯一有效** |
| 设计器三点菜单（teleport） | ✗ DOM 快照抓不到 | ✓ 坐标点击 |

**经验法则**：portal 元素一律用坐标；坐标点击后无反应 ≠ 没成功——**推送类操作静默成功**，用发布工作区 UI 或数据库验证。

### 6.2 菜单/对话框的坐标参考（1200x671 视口）

- 设计器三点菜单展开后：第一项「推送工作区」约 (1015-1122, 58-118)（表单设计器 y≈58，列表设计器菜单已展开时 y≈118）
- 「生成代码」对话框关闭：X (869, 128) 或「关闭」(655, 529)
- 未保存提示「确定」：(762, 377) 附近
- 发布说明对话框：文本框 (600, 225)，发布 (788, 321)
- 绿色小箭头是 **CUA 合成鼠标指针的渲染**，不是页面元素——别把它当目标点

### 6.3 加载与路由

- hash 路由直接 goto/tabs_new 常 404 或白屏 → 等 3-5s；仍白屏就 reload 或从 dashboard 重新点
- 页面加载慢时 DOM 快照为空 → sleep 后重读，别急着判定失败
- 每次关键操作后用截图/DOM/URL 验证再继续

### 6.4 配合数据库直连（只读）加速验证

浏览器操作几轮没结果时，直连数据库一步到位：

```python
from pp6kit.nlq import store, introspect
db = store.load()['db']
conn = introspect.connect(db['host'], db.get('port'), db['user'], db['password'], db['database'])
```

| 想确认什么 | 查哪里 |
|---|---|
| 发布工作区条目（含 XML 原文）| `iform_sync_workspace_item`（biz_type_: bo/form/data_template/dataset/rule；status_: WORKSPACE→RELEASED；xml_content_ 推送时即生成）|
| 变更区数据源 | UI 数据未落在直连库可见的表里（运行时层），以 UI 为准 |
| 表单↔对象绑定 | `iform_form_bo`（form_id_ + bo_code_）|
| 对象的列表 | `iform_data_template_def`（bo_code_、dataset_key_）|
| 选择器配置 | `iform_form_selector`（本库 0 行）|
| 数据集类型分布 | `iform_data_dataset.type_`（table 113 / sql 30 / thirdparty 23 / bo 9 / view 2）|

**注意**：直连库与线上系统是否实时同步需先确认（写入 0 行 ≠ 推送失败，以 UI 为准）。

## 8. 批量抓取全量数据（2026-11-12 实测）

### 8.1 为什么不能靠点界面

列表是虚拟滚动：一页 20 条只渲染约 12 行 DOM。业务对象 195 条、表单 373 条、
列表 207 条、数据集 178 条 —— 纯靠翻页 + 读 DOM 要 60 轮以上，不现实。
**正确做法：浏览器登录拿登录态 → 用页面内 `fetch` 放大分页一次拉完。**

### 8.2 登录态在哪（踩了 3 次坑才对）

| 尝试 | 结果 |
|---|---|
| 复用 cookie（`JSESSIONID`） | ❌ 接口 401 |
| 读 `localStorage` 的 `...-access_token` | ❌ 只有 `dataType`/`datetime`，**没有 value** |
| curl 直接打登录接口 | ❌ 密码要 RSA 加密，明文报 `arraycopy: last source index 65 out of bounds` |
| **在页面里 hook XHR 抓请求头** | ✅ **唯一可靠** |

token 只活在**内存**（axios 默认 header），不落盘。所以必须 hook：

```js
window.__hdr=[];
(function(){const oO=XMLHttpRequest.prototype.open,oS=XMLHttpRequest.prototype.setRequestHeader,oSe=XMLHttpRequest.prototype.send;
XMLHttpRequest.prototype.open=function(m,u){this.__u=u;this.__h={};return oO.apply(this,arguments)};
XMLHttpRequest.prototype.setRequestHeader=function(k,v){try{this.__h[k]=v}catch(e){}return oS.apply(this,arguments)};
XMLHttpRequest.prototype.send=function(){try{if(this.__u&&String(this.__u).indexOf('gateway')>=0)window.__hdr.push({u:String(this.__u),h:Object.assign({},this.__h)})}catch(e){}return oSe.apply(this,arguments)};})();
```

### 8.3 认证头（四个都要）

```
X-Authorization-access-token: <JWT，约 719 字符>
X-Authorization-systemid:    1374344426255581184
X-Authorization-system-alias: PowerProject
lang:                        zh-CN
Content-Type:                application/json   ← 注意不是 application/js
```

> 坑：`Content-Type` 设成 `application/js` 会得到 **415**；`systemid` 漏了会 **401**；
> 只取第一条带 token 的请求不够 —— 登录那次请求没有 `systemid`，要挑**同时含 token 和 systemid** 的那条。

### 8.4 登录脚本骨架

```python
import os
from playwright.sync_api import sync_playwright
# 口令只从环境变量读：export PP6_TEST_PASSWORD=...（不要把明文写进脚本/仓库）
# 复用本机 Chrome，不下载 chromium
b = p.chromium.launch(channel="chrome", headless=True, args=["--no-sandbox"])
# 逐字输入，不要 fill —— Vue 对合成赋值不敏感
pg.click("input[name=username]"); pg.type("input[name=username]", "demo", delay=55)
pg.click("input[name=password]"); pg.type("input[name=password]", os.environ["PP6_TEST_PASSWORD"], delay=65)
pg.click("button:has-text('登录')")
pg.wait_for_function("()=>location.hash.indexOf('dashboard')>=0", timeout=45000)
```

> `wait_for_url("**/dashboard")` 会被 hash 路由卡住，用 `wait_for_function` 查 hash 更稳。

### 8.5 接口与参数对照

| 数据 | 接口 | 关键参数 |
|---|---|---|
| 业务对象清单 | `POST business/v3/bo/def/query` | `{parameters:[{key:"excludeDisabledModules",value:true}], requestPage:{pageNo:1,limit:2000}}` |
| **对象字段明细** | `POST business/v3/bo/def/manage?boDefId=<id>` | body `{}`；`data` 是**字符串化 JSON**，要二次 `json.loads` |
| 表单清单 | `POST business/v3/form/def/query` | 加 `Q^formDef.FORM_TYPE_^S=form` |
| **列表**模板 | `POST business/v3/data/template/query` | `Q^TYPE_^S=default` + `showType=list` |
| **选择器** | 同上 | `Q^TYPE_^SIN=dialog,select-dialog,valueSource` |
| 数据集 | `POST business/v3/data/dataset/query` | 同对象清单 |
| 模块树 | `POST business/v3/form/module/config/queryAll` | body `{}` |
| 分类树 | `GET platform/v3/cat/type/findTreeData` | GET，不是 POST |

> **最大的坑**：`data/template/query` 用 `Q^TYPE_^S` 还是 `Q^TYPE_^SIN`，
> 决定你拿到的是「列表」（default，207 条）还是「选择器」（203 条）。
> 早先按 path 去重采集，把「列表」页签的请求覆盖掉了，误以为是同一批数据。

### 8.6 列表接口不返回明细（重要）

- `bo/def/query` 的 `attrList` **恒为空** → 字段要逐对象调 `bo/def/manage`
- `form/def/query` 的 `formHtml` / `formFieldList` **恒为空**
- `data/template/query` 的 `fieldList` 207 个里只有 1 个有 → 列配置要单独取

批量抓 195 个对象详情约 3 分钟（195 次请求，每次 ~50–90KB）。
脚本见 `docs/线上数据盘点-20261112.md` 附录说明；产物在 `docs/线上抓取-20261112/`。
